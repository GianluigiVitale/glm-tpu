## Core equivalence claim: CONFIRMED (with caveats)

The claim "probe `addressable_devices_indices_map((num_experts,))` == exactly what `make_array_from_callback` reads" holds for this deployment:

- **Runtime shard path chain**: `VllmFp8MoEMethod.process_weights_after_loading` (fp8.py:410) → `process_quantized_moe_weights` → `shard_moe_weights_to_tpu` (moe_weights.py:727, 660) → `general_device_put` (layers/common/utils.py:128) → `jax.make_array_from_callback(t.shape, sharding, lambda index: t[index])` on the ray-multihost branch (utils.py:158-160; launcher sets `TPU_MULTIHOST_BACKEND=ray`). Staging sharding is `P(_get_expert_shard_axis(mesh))` = `P(ShardingAxisName.EXPERT)` when the EXPERT axes exist (moe_weights.py:648-656, 684-685) — the SAME spec the filter probes (loader:122). The later `_get_moe_weight_shardings` GMM_EP `P(EXPERT)` (moe_weights.py:565) and final `shard_moe_weights` operate on already-global TPU arrays (`not t.is_fully_addressable` → plain `device_put`, no host reads).
- **1-D probe vs 3-D weight [E,K,N] vs 4-D scale [E,kb,1,N]**: `P(EXPERT)` (5-axis tuple `('attn_dp','attn_dp_expert','expert','model','dcp')` under `NEW_MODEL_DESIGN=1`, sharding.py:51,133) shards ONLY axis 0. **Empirically verified on CPU** (jax 0.6.2, mesh (1,1,1,1,32,1), E=256/160): per-device axis-0 ranges of the 1-D probe == 3-D == 4-D exactly; `make_array_from_callback` requested exactly the probe's ranges; content round-trips; ranges partition [0,E) with multiplicity 1. Replicated spec → filter no-ops; missing axis name → `ValueError` → caught → full load (safe). Non-divisible E (250/32) → jax RAISES (no silent uneven shards) — falls back to full load = OOM, loud not silent. GLM-5.2: `n_routed_experts=256` (`/home/gianl/glm-tpu/reference/hf-repo/config.json`), divisible.
- **E == param dim 0**: model built by `initialize_model(vllm_config_for_load)` with `enable_expert_parallel=False` forced (vllm_model_wrapper.py:504) → vllm `ep_size=1` → `num_local_experts=256` full rows, identity expert→row map (routed_experts.py:149-151); deepseek_v2.py:329 passes `num_experts=config.n_routed_experts`. ## Numbered findings

**1. MED-HIGH (latent, silent-garbage class) — one config flag re-arms a rank-derived filter that silently overrides the sharding-derived one.**
`~/vllm-build/vllm/model_executor/model_loader/default_loader.py:392` — `DefaultModelLoader.load_weights` calls `self._init_ep_weight_filter(model_config)` AFTER `IncrementalModelLoader.load_model` has set `self.local_expert_ids` (vllm_model_loader.py:176-178). It re-ASSIGNS `self.local_expert_ids` (line 366) whenever `model_config.is_moe and enable_expert_parallel and enable_ep_weight_filter`. Today it early-returns only because `enable_ep_weight_filter` defaults False (`vllm/config/parallel.py:164`). Failure scenario: anyone passes the natural-looking `--enable-ep-weight-filter` (deployment already has `enable_expert_parallel=True`, bench/engine.py:71): ep_size = dp·pcp·tp = 32 from `parallel_config.tensor_parallel_size=32`, but `get_tensor_model_parallel_rank()=0` on EVERY host (tpu_worker.py:326-335 initializes vllm distributed as world_size=1/tp=1) → every host loads experts {0..7}; the callback still reads its mesh-derived ranges → up to 248/256 expert rows are `torch.empty` garbage, outputs plausible-but-wrong, and nothing raises (see finding 2). Applies to the `tpu_streaming_loader` path; the live `runai_streamer` path is immune only because its `load_weights` override (loader:193-220) never calls `_init_ep_weight_filter`. The commit message's "parent consults local_expert_ids natively" is true only while vllm's own initializer stays disabled; there is no guard/assert.

**2. MED — zero verification that filtered loading actually wrote every local row; quantized models bypass vllm's completeness tracking entirely.**
`default_loader.py:402-404`: strict `track_weights_loading` only when `model_config.quantization is None` — GLM is fp8, so OFF; the runai override additionally discards `model.load_weights`' returned `loaded_params` (loader:220), and `DeepseekV2ForCausalLM.load_weights` doesn't raise on missing experts. Failure scenario: a missing/renamed/truncated expert tensor in the 755.7 GB staged checkpoint, or any future name-pattern drift vs `_EXPERT_ID_RE` (ep_weight_filter.py:17), leaves a LOCAL `torch.empty` row unwritten; the callback ships it to TPU; the router selects it occasionally → silently degraded numbers. The GSM8K n=4 smoke (top-8 of 256 experts × 75 MoE layers) exercises a small fraction of expert rows and is weak evidence against a handful of garbage experts. No cross-host check exists that the 8 hosts' id-sets are disjoint and cover [0,256).

**3. MED — the filter is coupled to the runtime placement only by convention (same `P(EXPERT)` literal in two files), not by construction, and is not keyed to backend/use_ep.**
loader:122 vs moe_weights.py:565/685. `compute_local_expert_ids_from_sharding` fires for ANY multi-process MoE load regardless of `moe_backend`. Today all reachable paths stage experts with axis-0 `P(EXPERT)` (verified incl. GMM_TP: staging is still expert-sharded, the TP reshard happens on-device), so no divergence. But a future backend whose FIRST host→TPU transfer is not axis-0-expert-sharded (e.g. a DENSE_MAT/MEGABLX implementation, or changing `shard_moe_weights_to_tpu`'s `_get_expert_shard_axis` fallback `mesh.axis_names[0]` at moe_weights.py:656 to something reachable) breaks it SILENTLY. Suggest: derive the id set inside `shard_moe_weights_to_tpu`'s module (single source of truth) or assert at shard time that callback indices ⊆ loaded ids.

**4. LOW-MED (latent) — EPLB redundant experts would desynchronize probe shape from param shape.**
vllm's own filter refuses to run under EPLB (`default_loader.py:340-342`); the sharding-derived filter has no such guard. With `num_redundant_experts=R>0`, param dim0 = 256+R (deepseek_v2.py:1279-1280, FusedMoE global slots) while the probe uses (256,). If 256+R divides 32 evenly the slices differ in width → hosts load 8-wide chunks, callbacks read wider ones → garbage rows served silently; if not divisible, loud jax error. Not live (EPLB off), worth a one-line `if eplb: return None`.

**5. LOW — "skipped rows … are never read" is inaccurate; PWAL reads and copies them (RSS accounting, not correctness).**
`t2j` (tpu_inference/utils.py:88-91) does a full `.numpy()` view + `jnp.array(bytes)` copy of each layer's ENTIRE expert tensor (garbage rows included, read as kernel zero-pages) before the callback slices local rows. Bit-preserving elementwise copy, no cross-expert reductions anywhere before the slice (checked `_process_moe_weights_no_requant`, `process_moe_weights`, `_requant_expert_batch_fn` — all reductions are within-expert over axes (1,2)/blocks; no `nan_to_num`/global max in these files), so fp8 garbage bits cannot propagate. But per-layer transient host RSS ≈ full-layer expert bytes (~9.7 GB for 256×(2·2048)×6144 fp8 + w2), relevant near the 95% Ray kill threshold.

**6. LOW — incremental per-layer sharding trigger silently disabled for filtered unquantized MoE (not the live fp8 path).**
unquantized.py:383-384 completes a layer at `len(_loaded_weights) == global_num_experts*3` keyed on `(expert_id, shard_id)`; with non-local weights skipped the count never completes → per-layer TPU offload never fires; all local rows stay on CPU until final PWAL (memory regression only — final PWAL uses the same `P(EXPERT)` so correctness holds). Side observation: for fp8 the pair-set is fed by BOTH weight and scale loads under the same key, so `VllmFp8MoEMethod` not being a `VllmQuantizationMethod` (fp8.py:384 — wrapper's isinstance check fails, per-layer path inert) is what saves it from an ordering-dependent early fire; that immunity is accidental.

## Attacks attempted and refuted

- **Garbage SCALES of non-loaded experts**: refuted. `should_skip_weight` (ep_weight_filter.py:79) skips only names ending `.weight`; every `weight_scale_inv` row of all 256 experts is loaded on every host, so scale rows shipped per-device are always real checkpoint data; weight↔scale pairing is by identical row index (identity map, ep_size=1 at build). Garbage exists only in non-local weight rows on host CPU and is dropped at the callback slice. `nan_to_num`/cross-expert-max: none found in the load path; requant reductions are per-expert; the live path is no-requant anyway (`DISABLE_WEIGHT_REQUANTIZATION=1`, `REQUANTIZE_WEIGHT_DTYPE=float8_e4m3fn` ≠ bf16 so `_v4_dequant_to_bf16` gate is off — launch_glm_32chip.sh:60).
- **Mesh divergence across modules**: refuted. Single mesh object: runner → `VllmModelWrapper.__init__` → `get_tpu_quantization_config(vllm_config, mesh)` → `VllmQuantConfig.set_configs` class attrs (quantization/__init__.py:55, configs.py:110-128); both `get_linear_config` and `VllmFp8MoEMethod(self, layer, self.mesh)` (fp8.py:106-111) use it. `ShardingAxisName` is one lazy singleton imported by both filter and moe_weights; only override in tree is VIT-only (sharding.py:360).
- **Shared experts / gate bias / dense-first-3-layers mis-skipped**: refuted — regex requires `.experts.<digits>.`; `.shared_experts.` and `mlp.gate.*` don't match.
- **Runai wiring**: `_get_weights_iterator(model_or_path, revision)` signature matches parent; `_is_distributed` only affects CUDA device targeting.
