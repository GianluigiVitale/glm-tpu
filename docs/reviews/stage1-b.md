2. **MED — env var name breaks the envs.py convention; `DISABLE_DSA_INDEXER=1` is silently ignored.** `tpu_inference/envs.py:317-318`: dict key/attribute `DISABLE_DSA_INDEXER` reads `env_bool("TPU_DISABLE_DSA_INDEXER")`. 3. **MED — the arch is registered but the real engine cannot start; the env gate covers only the indexer *forward*.** Two gaps the 1-chip harness (which hand-builds kv caches and never touches the runner) cannot see: (a) with the env var **unset** (default), `mla_attention.py:340` runs vLLM's `Indexer.forward` → `SparseAttnIndexer`/`DeepseekV32IndexerBackend` (GPU path) on TPU — GLM-5.2 is selectable but broken by default, and nothing in `_maybe_patch_for_glm_moe_dsa` warns or forces the flag; (b) even with the flag set, `Indexer.k_cache` (`DeepseekV32IndexerCache`, deepseek_v2.py:574-587) self-registers into `static_forward_context` on all 21 'full' layers, and `tpu_inference/runner/kv_cache_manager.py:672` then does bare `attn_module.kv_sharing_target_layer_name` → **AttributeError** (the class defines no such attr; `AttentionLayerBase` doesn't either; only `is_cache_for_ds_v4` classes at kv_cache_manager.py:62 are special-cased). Failure scenario: `vllm serve` GLM-5.2 with `TPU_DISABLE_DSA_INDEXER=1` crashes at KV-spec collection, before any forward. A maintainer will ask for the runner-side cache handling (DSV4 precedent exists) in the same series as the registration.

4. **MED — the W_UV_scale sharding fix (the one that only matters at head-TP>1) ships with zero coverage and its stated validation ran at TP=1.** `mla_attention.py:166-172`; glm-tpu f4ee4da says "GREEN on **1 chip**" and the harness itself documents multi-chip metadata is broken ("cross-shard class"). Note also the harness docstring (4-chip `TPU_VISIBLE_DEVICES=0,1,2,3` pin) contradicts the "1 chip" run claim — provenance is ambiguous.

5. **MED — monkey-patch shape: duplicates upstream's schedule logic with different precedence; the root fix belongs in vLLM upstream.** `vllm_model_wrapper.py:170-228`: upstream deepseek_v2.py **already** computes per-layer `_skip_topk` from `index_topk_pattern`/`index_topk_freq`/`index_skip_topk_offset` (lines ~1023-1032) but never reads `indexer_types` and still constructs an `Indexer` on every is_v32 layer; the HF reference (modeling_glm_moe_dsa.py:406-407) sets `indexer=None` from `indexer_types` alone. The installed GPU vLLM (`GlmMoeDsaForCausalLM` = bare `DeepseekV2ForCausalLM` subclass, deepseek_v2.py:1748) therefore has the identical IndexShare load failure — this is an upstream vLLM bug, and the clean upstreamable fix is a one-liner there (`indexer = None if _skip_topk`), not a tpu-inference constructor wrap. Maintainer pushbacks on the wrap as written: (i) two schedule implementations that can drift (patch checks `indexer_types` → `pattern` → formula; upstream checks `pattern` → formula); (ii) module-global `_ds2.Indexer` mutation is not thread-safe and the assignment sits *before* the `try:` (unrestored if `patch.object` throws); (iii) the wrapper is positionally coupled to `Indexer.__init__`'s 8-arg prefix position — an upstream signature insertion mis-binds `prefix` silently and `extract_layer_index` then parses the wrong string.
