## Findings (ranked)

1. **HIGH — real-serving KV-spec path is untested and will crash on the real model.** `tpu_inference/runner/kv_cache_manager.py:640-643` reads `attn_module.kv_sharing_target_layer_name` / `.attn_type` on every `AttentionLayerBase` in `static_forward_context` (collected at :575-577). vLLM's `Indexer` (built on all 20 `full` layers even with `TPU_DISABLE_DSA_INDEXER=1`) constructs a `DeepseekV32IndexerCache` that self-registers into `static_forward_context` (vllm deepseek_v2.py:574-601, :655-660) and defines neither attribute → **AttributeError in `get_kv_cache_spec` at engine bring-up**. DSV4's equivalent is special-cased via `is_cache_for_ds_v4` (kv_cache_manager.py:62-74); the DSV3.2/GLM class is not. The harness never sees this: it hand-builds caches and `layer_name_to_kvcache_index`, bypassing worker/runner/KVCacheManager entirely — "engine forward" in the commit message is a manual `torch.func.functional_call`, not the engine.

2. **HIGH — `TPU_DISABLE_DSA_INDEXER` does not propagate to Ray workers.** `TpuPlatform.additional_env_vars` (tpu_platform.py:117-133) is the multi-host env allow-list consumed at `executors/ray_distributed_executor.py:373`; the commit does not add the new var. On the 8-host pod (Stage-1's actual target) workers 1-7 get `DISABLE_DSA_INDEXER=False` → `self.indexer(...)` (mla_attention.py:340) runs vLLM's GPU `SparseAttnIndexer` CustomOp with a CPU-allocated `topk_indices_buffer` on TPU activations → worker crash/divergence only on non-driver hosts. This is the exact `GLM_*`/`DSV4_*` raylet landmine CLAUDE.md documents. Harness is single-process, so nothing covered it.

3. **HIGH — FP8 is unvalidated, and FP8 is the only deployable configuration.** The green run is bf16 (fork commit + glm-tpu f4ee4da claim only bf16 results; `--fp8` exists at glm_engine_parity.py:241 but no result is claimed anywhere, and docs/RESEARCH_LOG.md has no parity entry at all). The real model exists only as FP8 (~744 GB; bf16 doesn't fit 1024 GB HBM per CLAUDE.md). Untested: vLLM Fp8Config block-quant loading (mini block 64 vs real 128), fp8 MoE, the fp8-wk/bf16-weights_proj fusion upcast (deepseek_v2.py:750-780), and the fork's requantize/in-kernel dequant path. Also untested is the *quantized* branch of `_maybe_quantize` (mla_attention.py:146-155) in engine context: with `kv_cache_dtype=auto` the run exercised only the new identity branch — whichever KV dtype Stage-1 serving picks, one of the two branches has never run end-to-end.

4. **MED — both MLA "fixes" validated only at head-TP=1, where they are no-ops.** Fix (b) exists solely for head-TP>1 (`P(ATTN_HEAD,)` on a size-1 axis is only indivisible when the mesh product >1), yet the run was 1 chip — glm-tpu f4ee4da admits "model-axis sharding of this harness's hand-built metadata token-shards q/kv inconsistently — multi-device validation goes through the real runner on the pod instead". So the IndivisibleError repro/fix was never executed; also note `ATTN_HEAD = ('model','expert','dcp')` (sharding.py:47) — on the pod the shard product can exceed the mini's 4 heads entirely. Meanwhile glm_engine_parity.py:16-21 still instructs the 4-chip run the commit says is broken (doc/actual mismatch, see #10).

5. **MED — decode, mixed batches, chunked prefill, cache continuation, and multi-page sequences: zero coverage.** The harness issues exactly one forward with `request_distribution=[0,0,1]`, `query_start_loc=[0,T]`, T=32 < PAGE=128 → single prefill, single page, no second step ever reads back written KV (a slot-indexing bug in the cache write would be invisible). Kernel cases `decode_only`/`batched_decode`/`mixed` (kernel.py:2221, :2520-2555), `chunk_prefill_size`, and multi-page block-table logic never run. `tuned_params.py` keys are all `(num_q_heads=128, lkv=512, r=64, fp8/fp8)` — neither the mini (4/256/32/bf16) nor real GLM (64-heads-global, bf16 q) matches any key, so real decode runs on default `TunableParams` — the exact regime where the DSV4 long-context VMEM bug (fork commit ee915480) lived.

6. **MED — mini-dim aliasing hides the real-dim shape/padding class.** Mini: NOPE==VHD==IDX_HD==64, H==KV_LORA==DENSE_INTER==256, real: nope 192 ≠ v 256 (v>nope!), kv_lora 512, q_lora 2048, 64 heads, rope 64. Value-corrupting transposition bugs would NOT cancel (elementwise diff vs a same-weights reference catches them if above the floor — see #7), but bugs that are *shape-silent at equal dims and crash/mis-pad only at real dims* (nope/v split-order asserts, v-head 256=2×128 padding, `get_padded_num_heads` at 64 heads/32-way shard) are structurally invisible to this harness. Real rope 64 and mini rope 32 do pad to the same 128 (kernel.py:377), so that path is equivalent — but nothing exercised `qk_head_dim=256` scaling or `q_lora 2048` fused-proj splits at real ratios.

7. **MED — "parity green" is not machine-checked and the margin is thin.** `glm_engine_parity.py:302-305`: `main()` unconditionally `return 0`; no threshold assert anywhere — GREEN is a human reading printed diffs. Claimed numbers (f4ee4da): final_hs 0.344 vs bf16 floor 0.375 (92% of floor), logits 0.106 vs 0.127 (83%) — one seed, one input, T=32, s=0.05 weights (weakly-excited attention, logit std ≈0.3); a small systematic error can sit under this floor. And the commit's "per-layer within noise" is **not measured**: the bf16 control (lines 277-279) diffs only `final_hs`+`logits`; per-layer diffs are printed vs fp32 with no per-layer floor. "top-1 100%" = 32 tokens over vocab 512.

8. **MED — the "native ckpt keys verified against the real model.safetensors.index.json" claim is unverifiable on disk, with a concrete counter-signal.** No index.json exists anywhere in ~/glm-tpu (only config/README/tokenizer in reference/hf-repo). The real config's `modules_to_not_convert` names `model.layers.N.self_attn.indexers_proj` on exactly the full-indexer layers — a module that exists in neither the HF modeling file (which has `indexer.weights_proj`, modeling_glm_moe_dsa.py:194) nor vLLM. If the FP8 checkpoint really stores indexer projections under `self_attn.indexers_proj`, the loader mapping the mini validated (via `indexer.weights_proj` → fused `wk_weights_proj`) is not the mapping the real load will need.

9. **MED — the untested indexer-ENABLED path is the out-of-box default.** `envs.py:317-318` defaults `DISABLE_DSA_INDEXER=False`, so plain `vllm serve zai-org/GLM-5.2-FP8` on TPU executes `self.indexer(...)` (mla_attention.py:340) — never run on TPU, CPU-device buffer, GPU CustomOp — even single-host. Registering the arch without TPU-defaulting the gate on (or failing fast) ships a known-untested crash as the default experience.

10. **LOW — internal claim inconsistencies.** Harness docstring (glm_engine_parity.py:16-21) prescribes the 4-chip command; both commits say 1 chip and the multi-chip mode is admitted broken. Fork commit says "engine forward"; no engine (scheduler/runner/sampler/compute_logits — harness computes logits by hand at :199-201) ran. RESEARCH_LOG.md contains no parity entry (repo discipline says staleness is a bug), so the claimed numbers have no stored run record.

11. **NIT — `envs.py:317-318` is the only entry in the file whose dict key (`DISABLE_DSA_INDEXER`) differs from its env var (`TPU_DISABLE_DSA_INDEXER`);** setting `DISABLE_DSA_INDEXER=1` in the environment silently does nothing. NIT — `_maybe_quantize` maps any non-bf16 `act_dtype` (e.g. float16) to f32 weights (mla_attention.py:149-150). **On question (2) (cancellation at random weights):** elementwise comparison against a same-weights reference means value-changing transposition bugs cannot cancel (random matrices aren't symmetric); the residual exposure is (a) errors under the thin 8-17% floor margin at one seed, (b) equal-dim shape-silent bugs (#6), (c) unexecuted paths (#1-5).
