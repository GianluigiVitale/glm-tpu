## Adversarial review — f8332e80 (Stage-2c sparse-MLA decode kernel), CPU-only, TPU untouched

### FINDINGS

**F1 — MEDIUM | false "degrades to output 0" safety claim for fully-masked rows**
`tpu_inference/kernels/dsa/sparse_mla_kernel.py:18-19, 93-96, 190-191`
Claim: seg_valid==0 row "degrades to output 0, not NaN" (module docstring, `_finalize` docstring, entry docstring). **False.** When ALL columns are masked, `m == _MASK_VALUE`, so `p = exp(s - m_new) = exp(0) = 1` on *every masked column* (the underflow-to-0 argument only holds when a live score has lifted `m` above `_MASK_VALUE`). Output = `sum(v_rows)/(seg_len+1)` ≈ the **mean of the gathered garbage rows**, and NaN IS possible if any garbage row contains NaN. Probe (all-`-1` index row through `gather_kv_segment` → `dsa_sparse_decode`): `seg_valid=0`, output finite, `|out|max = 3.484` (exactly the clamped cache row), not 0. The XLA oracle has the identical pathology, so Gate K can never catch it (consistent-wrong pair). Reachability: padded batch slots with kv_len=0 give `seg_valid=0` through the gather in serving (gather itself has no >=1 contract — cross-contract gap with the kernel docstring). Harmless while pad-slot outputs are discarded, but the docstring invites relying on zero-latent (e.g. MTP plumbing). Fix: correct the three docstrings, or zero masked `p` (`p = where(j_abs < n_valid, p, 0)` is one extra `where` per tile) if graceful-zero is wanted as a real guarantee.
Note: for any `seg_valid >= 1` the pathology is unreachable — tile 0 always contains column 0 (valid), so `m` is live before any fully-masked tile; the masked-tail-inert test is genuine.

**F2 — MEDIUM-HIGH (integration notes, not committed code) | write-then-attend bullet is wrong for mla.v2; sparse path has no latent-cache writer**
`~/glm-tpu/docs/01-dsa-kernel-design.md:272-273` claims "The just-written token's latent is in the cache before the kernel runs (mla.v2/dsv4 both write-then-attend; kernel read-only over cache, kernel.py:319-320)". The `kernel.py:319-320` citation is the **DSV4** kernel's contract (dsv4 layer does an explicit XLA scatter before its read-only kernel, `deepseek_v4_attention.py:1876`). mla.v2 is the opposite: the write is **fused inside** the attention `pallas_call` (`new_kv_c`/`new_k_pe` operands, `donate_argnames=("cache_kv",)`, `mla/v2/kernel.py:2169,2505-2508`; serving passes k/k_rope straight in, `attention_interface.py:674-690`). In a sparse decode step mla.v2 does not run, so **nothing writes the new token's latent to HBM before `gather_kv_segment`** — the self index (always selected: highest indexer score) gathers a stale/uninitialized row. Stage-3 must add an explicit pre-gather scatter into the token-major view (and gather from the post-write array to respect SSA ordering under jit). Kernel-only commit is unaffected; the integration plan as written would ship this bug.

**F3 — LOW | `seg_block = min(seg_block, seg_len)` bypasses the 128-multiple assert**
`sparse_mla_kernel.py:210` asserts `seg_block % 128 == 0`, but `:230` then takes `min(seg_block, seg_len)`. Any `seg_len < seg_block` that is not a 128-multiple (tiny-topk test configs, seg_len=64) silently yields a non-128 tile: verified it runs and is *correct* under interpret, so CPU tests will never flag it — it surfaces only as a Mosaic compile error (or silent mis-tile) on real TPU. Move the assert below the `min`, or assert `seg_len % 128 == 0`.

**F4 — LOW | gather robustness gaps (all within documented contracts, worth debug asserts for upstreaming)**
`sparse_mla_kernel.py:342-347`: (a) an index `t >= page_size*max_blocks` or `t >= kv_len` silently clamps (`jnp.take`/`take_along_axis` default clip) → finite wrong latents, no error; (b) a violated -1-suffix contract (interleaved -1s) makes count-based `seg_valid` mask *valid tail entries* while attending clamped row-0 garbage mid-segment — no runtime check exists; (c) handing it the `MLA_TRANSPOSE_KV_CACHE=True` layout `[pages, 640, ps]` fails only via the downstream `lkv + r_dim <= kv_width` assert with a confusing message; docstring never mentions that mode (default False, `envs.py:411`); (d) int32 flat-row math caps cache at 2^31 rows (~2.7 TB latent — fine).

### REFUTATIONS

**R1 — Attack (1), the packed-cache reshape ordering: REFUTED, with a discriminating test.**
Write layout ground truth: upstream v1 reference `update_kv_cache` (`mla/v1/kernel.py:83-94`) places token `t` at `page=block_tables[t//ps]`, `row=(t%ps)//packing`, `col=(t%ps)%packing` — exactly row-major; upstream `mla_v2_test.py:397-402` pins the v2 Pallas fused writer to this reference **bit-exactly** (`rtol=0, atol=0`) over every valid token slot on TPU. Discriminating test (writer = v1 reference, an independent (row,col) convention, NOT the port's reshape; loud 1e6 garbage elsewhere, shuffled pages, cross-page tokens, mid-word sequence ends): reshape+gather round-trips exact per-token values including k_pe columns [512:576] and zero pads [576:640], for kv_packing ∈ {2, 4, 32} — including the serving default `MLA_KV_PACKING_SIZE=32` (`envs.py:404-405`) — and page_size ∈ {8, 32, 64}. Script: `/tmp/claude-2001/-home-gianl/8712a40e-7bbe-436d-b0ad-d676cbd502d5/scratchpad/discriminating_gather_test.py` (ALL OK). Residual risk is narrow: upstream only exercises v2-Pallas≡v1-ref at fp8/packing=4 (`mla_v2_test.py:217-218`); at packing=32 the misaligned decode write goes through `pack_new_kv`'s `num_sublanes>1` `pltpu.roll` branch (`kv_utils.py:151-184`) with **no upstream test**. I attempted the true Pallas write-then-gather on CPU: both interpret modes fail (`interpret=True`: dynamic-size DMA in `_copy` untraceable; `pltpu.InterpretParams`: `BitcastTransform` unsupported) — see on-TPU list. Stage-1's dense HF prefill parity transitively pins token order at packing=32 (word-granular causal masking would break under any permutation), so residual risk is low.

**R2 — Attack (2), -1 interleaving: impossible from both shipped producers.**
`indexer_kernel.py` `hierarchical_topk` overwrites slots `>= n_valid` **positionally** (`fill = iota >= n_valid`, :413-414) — suffix by construction, and `n_valid = min(kv_len, topk)` equals the gather's count exactly; slots `< n_valid` hold only finite-scored (relu >= 0) real positions since any finite beats the -inf invalid fill in `lax.top_k`. Stage-2a `topk_indices_from_scores` (`glm_dsa_indexer.py:413-415`) is value-based (`vals == -inf → -1`) but top_k's descending sort makes -inf a strict suffix. Duplicates impossible (disjoint per-block candidates). Only NaN scores could break the suffix (NaN sort order) — indexer must stay NaN-free; no runtime guard (F4b).

**R3 — Attack (3), seg_valid==0 in serving:** unreachable for live sequences — `n_valid = min(kv_len, 2048)`, decode kv_len >= 1 (>= 2 in practice: >=1 prompt token + self), and IndexShare shared layers (`glm_dsa_indexer.py:688-694`) reuse indices from the SAME forward pass / same kv_len, so no shared layer sees a different n_valid. Reachable only via padded kv_len=0 batch slots → F1's behavior (finite garbage mean, discarded), not NaN unless the cache holds NaN.

**R4 — Attack (4), parity bars: re-derived and measured, bars hold on CPU-interpret.**
fp32 2e-6: only kernel-vs-oracle deltas are tile-order reassociation of (m,l,acc) and `_finalize`'s `+exp(_MASK_VALUE-m)` ≡ +0.0 exactly; measured max 9.54e-7 over 5 seeds x 8 seqs x random seg_valid (2.1x headroom). bf16 2.5e-3: measured max 1.953e-3 = 2^-9 at observed |out| ≈ 0.29-0.47 → 2 ulps at [0.25,0.5) — the "1-2 output ulps" characterization is accurate. Caveat (not a bug, but PR-relevant): these bars are **interpreter artifacts** — CPU computes bf16 dots in fp32 and fp32 HIGHEST exactly; TPU MXU single-pass bf16 and 3/6-pass fp32 decompositions differ. The bars quoted in the commit message must be re-measured on TPU before upstreaming.

**R5 — Attack (5), reshape cost: no 5.4 GB/step materialization at serving defaults.**
`[pages, ps/32, 32, 640] → [pages, ps, 640] → [pages*ps, 640]` collapses **adjacent** dims; kv_packing=32 is a multiple of every TPU sublane-tile height (8 fp32 / 16 bf16 / 32 fp8), so the tiled physical layout is byte-identical → metadata-only bitcast, fused under jit. The gather's HBM traffic is the intended `R*2048*1280 B`. Two caveats: if `MLA_KV_PACKING_SIZE` were ever set below the dtype tile height the reshape becomes a genuine full-cache relayout per call (worth an integration assert), and the transposed-cache mode is incompatible outright (F4c). Direct packed-layout indexing is possible but buys nothing.
