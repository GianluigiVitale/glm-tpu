## Findings (numerics lens)

**1. MED — parity harness has no machine-checkable gate; "GREEN" is eyeball-only.**
`~/glm-tpu/parity/glm_engine_parity.py:222-233, 306-309` — `_diff()` only prints; `main()` returns 0 unconditionally. Failure scenario: any future fork rebase that reintroduces a numerics bug still exits 0; scripted re-validation/CI cannot detect the break, and the "below the bf16 noise floor" claim in commit 9bb2c23e is a human reading of stdout, not an assertion. Evidence: no comparison between the engine diff and the control diff exists anywhere in the file.

**2. MED — the noise-floor comparison is statistically weak and the recorded pass is marginal; systematic bugs ≲1% hide under it.**
`glm_engine_parity.py:66, 280-304` — the gate compares max|engine(bf16) − HF(fp32)| against max|HF(bf16) − HF(fp32)| at a single seed, single T=32. Recorded result (glm-tpu f4ee4da message): final_hs 0.344 vs floor 0.375 — an 8% margin on a max-statistic. Two problems: (a) under the *null* the two quantities are draws from ~the same distribution (engine bf16 rounding is just a different realization), so "eng ≤ floor" fails ~half the time even for a perfect port and passes narrowly here by luck; (b) under the *alternative*, any systematic relative error below ~1e-2 (bf16 eps 2⁻⁸≈3.9e-3 accumulated over 5 layers) is invisible and top-1 stays 100% — e.g. a wrong `rms_norm_eps` (1e-5 vs 1e-6 → ~5e-6 rel) or a ~0.5% error in `sm_scale`/`attention_scaling` passes cleanly. The decisive missing leg: the engine is never run at fp32 (`EngineArgs(dtype="bfloat16")` hardcoded at line 66); an engine-fp32 vs HF-fp32 leg would have a ~1e-5 floor and expose exactly this class. Also `rel` at line 230 is global `max|Δ|/max|ref|`, not elementwise — small-magnitude components are unchecked.

**3. MED — commit claim "per-layer within noise" is not backed by the harness.**
`glm_engine_parity.py:281-283 vs 287-289` — the bf16 noise floor is computed ONLY for `final_hs` and `logits`; the per-layer engine diffs are printed with no per-layer floor (the `hs16[i]` states exist and are unused). Failure scenario: a layer-0-local bug producing |Δ|≈0.3 (under the *final* accumulated floor 0.375 but ~10× the layer-0 floor) reads as "within noise." The commit message (9bb2c23e: "per-layer within noise") asserts a comparison the harness never performs.

**4. MED — the two references disagree on the indexer RoPE layout for GLM-5.2, and this parity is structurally blind to it (Stage-2 landmine).**
`~/glm-tpu/reference/modeling_glm_moe_dsa.py:238-239` — HF hardcodes NON-interleaved rope in the indexer (`apply_rotary_pos_emb`, comment "The indexer uses NON-interleaved (half-split) RoPE") and **never reads `config.indexer_rope_interleave`**; I verified the installed transformers file is byte-identical to this copy. The vLLM GPU impl honors the flag: `/home/gianl/vllm-build/vllm/model_executor/models/deepseek_v2.py:1007` `is_neox_style=not getattr(config, "indexer_rope_interleave", False)` → interleaved for GLM-5.2 (`configs/glm-5.2-fp8-config.json:25` = true). One of the two is wrong for the real checkpoint. Invisible here because (a) the engine indexer is disabled and (b) `index_topk ≥ T` makes HF's selection inert — so the harness validates zero indexer numerics despite the mini checkpoint shipping indexer weights. Failure scenario: Stage 2 validates the TPU indexer "against HF" and bakes in the wrong layout, or falsely fails against the GPU impl.

**5. LOW — both "latent upstream bug" fixes are code-consistent but run-unvalidated by the cited parity.**
`mla_attention.py:168-172` — the W_UV_scale resharding to `P(None, ATTN_HEAD)` only differs observably at head-TP>1; the parity ran on 1 chip (f4ee4da: "GREEN on 1 chip"; the harness itself notes multi-chip metadata is inconsistent), where the old `P(ATTN_HEAD,)` on the size-1 axis is also divisible. Likewise the `kv_cache_quantized_dtype != None` branch (`quantize_tensor`) never executed. I verified the axes by code-read (below), but the IndivisibleError repro/fix and fp8-kv path have no run evidence.

**6. LOW — fp16 activation dtype silently upcasts W_UK_T/W_UV to fp32 in the identity path.**
`mla_attention.py:149-150` — `act_jnp = jnp.bfloat16 if act_dtype == torch.bfloat16 else jnp.float32`. With `dtype=float16` the absorbed projections double in HBM and become dtype-inconsistent with f16 activations (numerically harmless; jax promotes). Should map float16→float16 or assert.

**7. LOW — indexer gate is env-dependent, not default-safe; env name indirection.**
`mla_attention.py:340`, `envs.py:317-318` — default `False` means serving GLM-5.2 without `TPU_DISABLE_DSA_INDEXER=1` runs vLLM's `SparseAttnIndexer` forward under torchax on TPU (untested; likely crash — though if it survives, outputs stay dense/correct since indices are discarded). NIT: the attr `DISABLE_DSA_INDEXER` reads env `TPU_DISABLE_DSA_INDEXER`; setting `DISABLE_DSA_INDEXER=1` does nothing (sibling entries like `FORCE_MOE_RANDOM_ROUTING` use their own name). NIT: `_layer_is_shared` in `vllm_model_wrapper.py` classifies an MTP layer (layer_id=78, out of `indexer_types` range) as 'full' via the formula — matches vLLM GPU behavior but is a Stage-3 loader risk if the MTP weights ship no indexer.

## Attacks refuted (explicit)

**(1) Identity-scale path — NO DEFECT FOUND.** Shapes verified exactly compatible with the quantized path and the forward einsums: `quantize_tensor(..., axis=1)` returns `scale = squeeze(axis=1)` (`quantization/__init__.py:264`) → `[N,L]` for W_UK_T `[N,P,L]` and `[N,V]` for W_UV `[N,L,V]`; the identity `jnp.ones((w.shape[0], w.shape[2]))` produces the identical shapes. `expand_dims(·,1)→[N,1,L]` broadcasts against the `'bnp,npl->nbl'` output `[N,B,L]` (`flash_attn_mla.py:151-157`); `expand_dims(·,0)→[1,N,V]` against the `'nbl,nlv->bnv'` output `[B,N,V]` (`flash_attn_mla.py:205-209`). The scales are constant along the contraction axes (P resp. L), so post-einsum multiplication is mathematically exact; ×1.0 in f32 before the `astype(input_dtype)` is a bit-exact no-op. The fix does not alter the `kv_cache_dtype=fp8` path (same `quantize_tensor` call). The commit's NaN diagnosis for `quantize_tensor(None,…)` is accurate by code-read: `np.dtype(None)`=float64 → dtype_max≈1.8e308 → scale underflows to 0 at the f32 squeeze, weights clip to ±1.8e308 → inf on the f32 cast → inf×0=NaN in the forward.

**(2) astype(bf16) precision loss — REFUTED.** W_UK_T/W_UV leave upstream PWAL already in `act_dtype`: `/home/gianl/vllm-build/vllm/model_executor/layers/attention/mla_attention.py:839-841` `get_and_maybe_dequant_weights(self.kv_b_proj, out_dtype=act_dtype)`, with the explicit upstream comment (836-838) that GPU also "stores fp16/bf16 copies and performs the bmm's in 16-bit." So `astype(bf16)` is a no-op, and TPU (bf16 inputs, f32 accumulation via `preferred_element_type`) is at parity or better vs GPU bf16 bmm. The previous behavior was NaN, so no regression axis exists.

**(3) Rope-layout bug hiding under the noise floor — REFUTED for the pairing-bug class** (the gate's real weaknesses are in findings 1-3). Numpy probe at the harness dims (ROPE=32, θ=8e6, T=32, positions 0..31): interleaved vs half-split pairing gives score delta max ≈1.86 on a score scale of ≈1.76 and attention-prob deltas ≈0.04 — ~10× the bf16 noise (~4e-3); the top frequency pairs rotate multiple radians by p=31, so no targeted probe is needed — the existing diff would catch it loudly. Caveat: the parity is inherently blind to conventions differing by a *joint* output permutation of q_pe/k_pe (vLLM GPT-J-style rope emits interleaved positions; HF `apply_rotary_pos_emb_interleave` emits half-split, `modeling_glm_moe_dsa.py:330-337`) — but those are dot-product-invariant and therefore not bugs.

**(4) HF dense-equivalence at index_topk ≥ T — CONFIRMED EXACT.** `modeling_glm_moe_dsa.py:261-262`: `topk = min(self.index_topk, T)` = T → `topk()` returns **all** T indices, so tie-breaking cannot drop anything at k==T; `:461-465`: `index_mask = ones.scatter(-1, topk_indices, False)` → all-False; `:470`: `masked_fill(all-False, min)` leaves the additive causal mask bit-identical, and the op only ever ADDS `finfo.min` (it can never unmask future positions even though topk "selects" them); eager ignores `sparse_indices` (459, 471-472, 485). The harness enforces the precondition (`glm_engine_parity.py:247` asserts T ≤ IDX_TOPK=128) and uses `attn_implementation="eager"` (`glm_engine_common.py:270`). No residual DSA effect exists in the reference at these settings.

**Model-loader/registration changes (`model_loader.py:54-68`) and the Indexer monkeypatch signature (`vllm_model_wrapper.py:196-212` vs `deepseek_v2.py:1009-1019`): no numerics findings** — the patch matches the vLLM call site positionally incl. `is_inplace_rope` via kwargs, and the shared/full schedule formula matches both HF (`configuration_glm_moe_dsa.py:136-146`) and vLLM (`deepseek_v2.py:1027-1034`), including the default offset 2.
