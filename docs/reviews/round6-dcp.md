## Findings (most severe first)

### F1. LOW-MEDIUM (claim accuracy): the kernel's default-path traced program is NOT byte-identical to the pre-change checkout

- **File**: `tpu_inference/kernels/mla/v2/kernel.py` (the `src_kvc`/`src_kpe` and `dst_kvc`/`dst_kpe` hoists in `_fetch_bkv` ~1105-1152 and `_update_kv_cache` ~1562-1592, introduced by the `if _INTERPRET: ... else: ...` refactor).
- **Claim attacked**: kernel header comment "The default (False) leaves every traced program byte-identical to the original" (line 16) and `_mla_ragged_paged_attention_impl` docstring "the original entry point; ... traced program unchanged".
- **Evidence**: I traced `mla_ragged_paged_attention` on identical inputs from the parent checkout (`git show 29a51331~1:...kernel.py`, loaded standalone) and from the current tree — SHA-256 of the jaxpr text differs (`e4fcdb6a…` vs `34ddee03…`). Structural diff: exactly 18 hunks, every one the same pattern — two scalar ops (a `page_indices` SMEM read + `mul 8`) hoisted above the first `dma_start` of a kvc/kpe pair, because the refactor now builds both `src/dst` refs before issuing either copy. All 45 `dma_start` ops keep identical order and operands. Repro: `scratchpad/jaxpr_hash_check.py` (+ `jaxpr_par.txt`/`jaxpr_cur.txt` dumps).
- **Failure scenario**: none numerically — the dataflow graph is identical, so outputs are bit-identical by construction. But the gate-off "byte-identical" guarantee holds only at the `mla_attention` level *with the kernel mocked out* (which is what `test_gate_off_traced_jaxpr_byte_identity` traces, and which I confirmed cross-checkout, see C7). A gate-off production run on TPU re-traces and re-compiles a (trivially) different kernel program; if Mosaic's scheduler is sensitive to the scalar-op placement, timing (not values) could shift. The commit message's "equals the pre-change checkout's hash (916358e5...)" is a mocked-kernel statement and should be worded as such; also note the test does **not** actually pin that hash constant — it only asserts internal three-way equality.
- **Suggested action**: soften the two "byte-identical / traced program unchanged" comments to "dataflow-identical (only scalar address computations are hoisted above the paired dma_start; DMA order and operands unchanged)"; optionally do a one-off on-TPU gate-off logit spot-check after the first deploy.

### F2. LOW (dead code + fragile invariant): `init_empty_shard_scratch` is unreachable; the empty-shard guarantee rests entirely on the clamp + mask-value margin

- **File**: `kernel.py:2166-2177` (`@pl.when(num_bkv == 0)`), `kernel.py:1920-1932` (clamp).
- **Analysis**: with `dcp_size > 1`, `num_bkv = max(cdiv(kv_len_max, bkv_sz), 1)` — never 0. With `dcp_size == 1`, `kv_len >= q_len >= 1` for every sequence in an active grid range, so `num_bkv >= 1` too. The `pl.when(num_bkv == 0)` init (m=-inf, l=1, acc=0) can therefore never fire; the *actual* empty-shard mechanism is the forced fully-masked block whose lse lands at `mask_value + log(l)`.
- **Failure scenario** (latent, not current): (a) someone later removes the clamp trusting the comment on the init block ("A shard whose LOCAL kv length is 0 ... runs zero bkv iterations") — the software-pipeline deadlock the clamp fixes returns immediately; (b) a future caller passes a custom `mask_value` above `-1e37` (`mask_value` is an exposed kwarg; other kernels commonly use ~-1e9): the fully-masked block's lse then clears the combine floor and its weight is nonzero only through exp-underflow — still numerically 0 whenever any shard holds real mass (exp(-1e9−m)→0), and all-masked rows are padding-only, so even this is benign today, but the floor invariant is silently load-bearing and unvalidated (`_mla_ragged_paged_attention_impl` could assert `mask_value < _DCP_LSE_FLOOR` when `dcp_size > 1`).
- **I verified the invariant holds now**: `mask_value = finfo(s_dtype).min` (kernel.py:2484) = −3.40e38 (f32, the v4 path) or −3.39e38 (bf16 default on v5+) — 34× below the −1e37 floor; `log(l)` adds at most ~+20.

### F3. LOW (test gap): the production `kv_lens_local` closed form is computed but never consumed by any test

- **File**: `attention_interface.py:821-826`.
- **Analysis**: in `tests/layers/common/test_mla_dcp.py` the mocked kernel does `del distribution, kv_lens` — the production formula runs but its value is discarded (the stand-in masks by global position instead). In `tests/kernels/test_mla_v2_lse_dcp_cpu.py`, the real kernel consumes local lens, but they come from `_local_lens`, a *test-local copy* of the formula. A transcription divergence between interface and test copy (e.g. `_dcp_idx * _p_g` instead of `* _p_l`) would pass **every** committed test and only fail on TPU (wrong fetch bounds → missing/extra masked keys).
- **Mitigation performed here**: I brute-forced the formula as written in the interface over a grid of (L, dcp∈{2,4,8}, P_l∈{2,4,8,64}, pack∈{1,2,4}) against the ground truth "count of owned positions < L" — 0 mismatches — and confirmed the two copies are textually equivalent. Repro: `scratchpad/attack_striping_lse.py`.
- **Suggested action**: have the interpret-mode kernel test import/derive local lens through a shared helper, or add an equality assert between the interface value and the striping ground truth in the mocked test (the mock receives `kv_lens` — assert before deleting).

### F4. LOW (test gap / dead default): `batch_flash_attention`'s DCP mask branch is unreachable in production and untested

- **File**: `kernel.py:532-544` (one-step path), vs `kernel.py:689-705` (two-step path).
- **Analysis**: `two_step_flash_attention` defaults to `True` (kernel.py:2431) and neither `mla_attention` nor the tuned params ever set it `False`, so production takes `flash_attention_step1_qk_softmax` — whose DCP branch the CPU interpret tests do exercise. The one-step `batch_flash_attention` strided-mask code is carried along untested. By inspection it is the same formula (global `q_span` from `kv_lens_global_ref`, strided `k_span`, sliding-window on global positions), so this is coverage debt, not a bug.

### F5. INFO (commit-message precision): the "dcp=1 bit-exact vs mla_ragged_paged_attention" test is a same-checkout comparison

- Both entry points in `test_lse_variant_bit_exact_at_dcp1` share the refactored `_mla_ragged_paged_attention_impl`; the test proves the LSE variant adds nothing at dcp=1, not that the refactor preserved the pre-change kernel. ## Attacks attempted and CONFIRMED sound (positive assurance)

**C1. Striping formula vs the actual upstream-#2398 code in this fork.** The engine is told `block_size *= decode_context_parallel_size` (`runner/kv_cache_manager.py:458`), the MLA cache is allocated with that global page size and sharded `P(BATCH, CONTEXT)` on dim 1 (`runner/kv_cache.py:132-140`), and GSPMD assigns dcp shard *s* the contiguous word rows `[s·P_l/pack, (s+1)·P_l/pack)` of every page. Hence: owner(pos) = `(pos % P_g) // P_l`, local row/sub = `(pos % P_l) // pack`, `(pos % P_l) % pack`, and the kernel inverse `g(x) = (x//P_l)·P_g + s·P_l + x%P_l` — all three exactly match the interface (`attention_interface.py:854, 859-861`) and kernel (`kernel.py:697-700`). Brute-forced as a bijection (owned positions ↔ local indices, monotone, `g(x) ≥ L` for every tail index `x ≥ n_s(L)`, scatter coordinates equal to the sharded-slice ground truth) over the full (L, dcp, P_l, pack) grid — 0 failures. `ShardingAxisName.ATTN_DATA` excludes `dcp`, so all metadata is replicated across the dcp axis (required for every shard to compute identical owner assignments); `md.query_start_loc` is padded with the repeated final cumsum (`tpu_runner.py:2493-2499`), so the interface's `searchsorted` is well-defined on padding.

**C2. Owner scatter has no aliasing.** For each valid token exactly one shard passes `_owner_t == _dcp_idx` (replicated metadata + brute-forced owner partition). Within a shard, distinct valid tokens map to distinct (page,row,sub): distinct positions within a sequence, distinct pages across sequences; padding tokens and `_pos_t < 0` are routed to page id `_total_pages` and dropped by `mode="drop"` (any OOB index drops the whole row). The same-slot-two-shards case cannot occur because a (page,row,sub) triple is local to one shard's slice — writes by different shards land in disjoint global cells by construction. Residual assumption (integration-level, pre-existing): vLLM never hands out a *shared* (prefix-cached) block for writing; copy-on-write guarantees this upstream. The mocked test's exact cache-equality assertion (`test_dcp_matches_replicated_reference`, pack ∈ {1,2}, dcp ∈ {2,4}, head-sharded on/off — re-run, passed) would catch owner/placement errors.

**C3. LSE math at the edge cases.** `lse = m + log(l)` is exactly the online-softmax log-sum-exp; the combine `out = Σ_s out_s·exp(lse_s − LSE)` is algebraically exact for disjoint per-shard key sets. Verified numerically (200 random trials vs f64 full softmax, ≤5e-6; plus the committed exhaustive-grid test). Edge cases attacked directly (`attack_striping_lse.py`): lse exactly at the floor (dropped), just above the floor next to a real shard (weight underflows to exact 0 — the floor's interaction with "genuine tiny logits" is benign because any genuine lse in (−1e37, −100] underflows against any sane m), two shards both just above the floor (finite, averaged — the f32-correct answer at that saturation), all-empty rows (exact 0, not NaN), NaN partial output on an invalid shard (suppressed by `jnp.where(valid, out, 0)` *before* the multiply — NaN·0 never happens), NaN lse (compare-false ⇒ invalid ⇒ dropped, and `m_safe` clamps a NaN pmax), single-token/single-shard degenerate (weight 1). `+inf` lse propagates NaN — identical to baseline softmax overflow, accepted. Crucially, **no valid row can be all-invalid across shards**: write-then-attend puts each query's own KV on its owner shard before the kernel, local lens include this step's tokens, and the diagonal is never masked (`q_span < k_span` is false at equality) — so every real row has ≥1 unmasked key somewhere.

**C4. The num_bkv≥1 forced block contributes exactly zero weight.** A shard has `n_s(L) = 0` iff `L ≤ s·P_l` (first logical block, low stripe elsewhere); then every local index maps to `g(x) ≥ s·P_l ≥ L > q_span`, i.e. the block is fully masked for that sequence — including the mixed case where other sequences in the same grid step have nonzero local length. All its fetch DMAs are size 0 with start/wait sizes computed from the same expressions (symmetric; the zero-size dummy-wait pattern pre-exists in ragged batches). The row then has m = mask_value, l = num_bkv·bkv_sz ≥ 1, out finite (possibly stale-garbage mean — irrelevant), lse ≈ −3.4e38 < −1e37 ⇒ weight exactly 0 (asserted in `test_dcp4_empty_shards…`, re-run, passed). The `exp(m_prev − m_curr)` chain stays finite (−inf − finite = −inf ⇒ 0).

**C5. Chunked prefill / history spanning shards.** Under `history_only`, `kv_left_frm_cache = kv_left` covers the full *local* length including the pre-scattered new chunk; the strided mask compares global q positions against global key positions, so history distributed across stripes is read correctly and in full. The committed interpret test covers a mixed chunk (11 cached + 7 new) straddling the stripe and the block boundary at dcp=2 with num_bkv=2 on shard 0, plus a straddling decode (16+1), and matches the dcp=1 run to 2e-5 with **exact** cache reassembly. The chunk-prefill pallas pass itself is inert in production (`chunk_prefill_size=None` from the interface; prefills go through MIXED), and multi-`bq` prefill (q_len > 8) under dcp is CPU-untested but shares the `bq_idx·bq_sz` q-span arithmetic with the tested non-dcp path.

**C6. Wiring/plumbing audit.** Scalar-prefetch order (7 base + `kv_lens_global`, `dcp_shard` appended) matches the kernel's `refs` unpacking, guarded by `assert _idx == len(refs)`; `input_output_aliases` offsets recomputed off `len(scalar_prefetches)` reproduce the original {7:0, 11:1} at dcp=1; the lse carry (init −inf) threads through all four passes via aliasing so padding rows stay −inf; `_send_bo` starts *and* waits the lse DMA under the same `sz > 0` guard and its own semaphore row (5th), incl. the epilogue; `wait_update_kv_cache`/`start_update_kv_cache`/`_pack_new_kv` are consistently disabled under `history_only` (and `update_szs` are provably 0 anyway since `kv_left_frm_new = 0`). Head-sharded composition removes `dcp` from the q/output head axes (ATTN_HEAD = ('model','expert','dcp') — the guard is real, not hypothetical); the token-sharded default always has `_gather_tokens = True` when dcp>1 (MLP_TENSOR contains 'dcp'), so the scatter always sees the full-T k/k_rope.

**C7. Gate-off byte-identity and gate hygiene — re-verified independently.** I loaded the *actual parent-commit* `attention_interface.py` and traced `mla_attention` (kernels mocked identically) on an 8-CPU-device dcp=2 mesh: SHA-256 equal to the current tree's gate-off trace (`5f467fa7…` both) — the commit's cross-checkout claim is true (hash values are env-dependent; equality is the claim). `GLM_MLA_DCP=1` on a dcp=1 mesh is a no-op; explicit caller shardings bypass the gate; transposed cache is rejected loudly (all re-run, passed). Env is read per-call, not import-cached.

## What only on-TPU runs can verify

1. **Pipeline liveness of the forced block on real hardware**: zero-byte `dma_start`/dummy-wait semaphore balance is a hardware contract the Mosaic interpreter does not model. Pre-existing pattern (ragged batches already produce zero-size fetches), but the *all-sequences-empty* grid step is newly reachable. A dcp≥2 decode with one 1-token sequence per batched-decode group is the minimal repro.
2. **Mosaic compile of the DCP variant**: strided-mask iota/div/mod chains, SMEM scalar (`dcp_shard_ref[0]`) inside vector masking, and the lse `[2, batch, bq_sz, H, 128]` f32 scratch + 5th DMA semaphore row. VMEM: at H=128 (token-sharded, all heads) and bq=8 the lse scratch alone is 4 MiB on a 16 MiB v4 — a compile-time fit check is mandatory before relying on the default path; head-sharded (H_local ≤ 16) is comfortable.
3. **kv_packing > 1 with dcp + emit_lse**: interpret mode is pinned to packing 1 (fp32); the mocked tests cover the *scatter* at pack 2 but the real kernel's dcp path has never executed with packed words (production bf16/fp8, `kv_packing` 2/4, `MLA_KV_PACKING_SIZE=32` layouts).
4. **End-to-end engine integration**: engine block tables actually arriving in `P_g`-token units at the metadata layer (the spec hack path), attn_dp × dcp interplay, prefix-caching page sharing vs the owner scatter (C2's CoW assumption), MTP/multi-token decode positions.
5. **Gate-off recompile equivalence** (F1): one logit spot-check gate-off vs pre-change binary.
6. **Performance**: the XLA scatter's cost per layer (mechanism (b) vs (a)), actual elimination of the per-layer cache all-gather, and the lse pmax/psum overhead.
7. **bf16 `s_dtype` on v5/v6** with dcp (CPU tests and v4 both run f32 scores).
