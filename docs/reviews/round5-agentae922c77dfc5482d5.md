## Findings (severity-ranked)

**1. CRITICAL — `params_from_vllm_indexer` reads the fp8-resident `wq_b.weight` without its scales → silently garbage indexer scores.**
`tpu_inference/layers/vllm/custom_ops/glm_dsa_indexer.py:221` (`wq_b = _oriented(as_jax_f32(indexer.wq_b.weight), ...)`).
Evidence chain, each link verified in-tree:
- vLLM builds `Indexer.wq_b = ReplicatedLinear(..., quant_config=quant_config)` (`/home/gianl/vllm-build/vllm/model_executor/models/deepseek_v2.py:628`), while `wk_weights_proj` is built with `quant_config=None` (fp8 wk is dequantized to bf16 at load by `_try_load_fp8_indexer_wk`) — so ONLY wq_b is quantized.
- GLM-5.2 checkpoint (`/home/gianl/glm-tpu/reference/hf-repo/config.json`): `quant_method: "fp8"`, block 128×128; `modules_to_not_convert` (541 entries) contains `indexer.k_norm` and `indexers_proj` but **no `indexer.wq_b`** → wq_b is fp8-block-quantized and not ignored.
- tpu-inference's registered `VllmFp8Config.get_quant_method` (`layers/vllm/quantization/fp8.py:85-97`) gives it `VllmFp8LinearMethod`; its `process_weights_after_loading` (fp8.py:173-260) stores `layer.weight` as the **fp8 array transposed to [in,out]** and the block scales in a **separate `layer.weight_scale`** (fp8-resident path; GLM launch uses `REQUANTIZE_WEIGHT_DTYPE=float8_e4m3fn`, docs/03-throughput-analysis.md:256). `fuse_matmuls` defaults True (`layers/common/quantization/configs.py:27`), so `.weight` is a single Parameter — `as_jax_f32` happily `jax_view`s the fp8 codes and casts to f32; `weight_scale` is never touched. With ue8m0/block scales the values are wrong by up to the full per-128-block scale factor.
- Failure scenario: `GLM_DSA_MODE=xla_ref` on the real model → indexer q is garbage → top-k selects wrong keys → sparse output silently wrong. **Gate D0 cannot catch this**: with topk >= T every causally-valid key is selected regardless of score order, so the dense-equality gate passes with garbage scores. The CPU tests are also blind: the mock indexer uses plain float `torch.from_numpy` weights (commit blob `tests/layers/vllm/test_glm_dsa_indexer.py:140-150`).
- Fix: dequantize in the adapter (`weight * expand(weight_scale)`, reusing `dequantize_tensor`), or force the indexer linears onto the unquantized/dequant-to-bf16 method. Add a parity gate that runs the adapter against an fp8-processed Indexer, not a float mock.
- On-TPU proof (1 line): `indexer.wq_b.weight.dtype == float8_e4m3fn` and presence of `weight_scale` on the loaded model.

**2. HIGH — `xla_ref` bypasses `self.mla_attn` entirely: latent KV cache is never read OR written, and the gate has no runtime guard.**
`mla_attention.py:439-446` + `_glm_dsa_xla_ref_attention` (mla_attention.py:490+).
Silently-wrong configs (no error raised anywhere — the only `NotImplementedError` is on the `k_cache=` argument the wrapper never passes, glm_dsa_indexer.py:438):
- ANY decode step: T=1, the token attends only itself (uniform softmax over one key) → garbage from the second generated token of every request.
- Chunked prefill: chunk N attends only its own keys.
- **Batched prefill of >1 sequence — NOT documented**: both the indexer's `mask_scores` and the oracle's causal bias are positions-only (`positions[None,:] > positions[:,None]`, glm_dsa_indexer.py:393, mla_attention.py:105). Two sequences flattened into one forward cross-attend wherever their absolute position ranges overlap (tok of seq B at pos 10 attends seq A's pos<=10). The "single-chunk prefill" claim must be "single-SEQUENCE single-chunk", and the tests only cover single-sequence.
- Honesty verdict: docstrings state validation-only/single-chunk and "cache is NOT read or written" (partially honest), but per-sequence batching is unmentioned and nothing enforces any of it — an engineer flipping the env in serving gets plausible-looking garbage, not a crash. PR-grade needs at least a loud guard (e.g., refuse when `md.request_distribution` implies decode/mixed via a checkify/debug assert, or rename the mode `xla_ref_unsafe_single_seq`).

**3. MEDIUM — S1 gate is unsafe on any mesh with ATTN_DATA/BATCH product > 1.**
`attention_interface.py:546-567`. `ATTN_HEAD=('model','expert','dcp')` excludes the `attn_dp`/`data` axes (`sharding.py:44-62`). Head-sharded in_specs declare q/k token-replicated across ALL other axes, but `md.*` stay `P(ATTN_DATA)` and cache `P(BATCH)` — on a DP-attention mesh each DP shard would pair the global token axis with its local metadata slice and local cache shard → wrong outputs and inconsistent cache. The token-sharded path avoids this by only gathering MLP_TENSOR. Latent today (GLM is pure TP-32), but the env gate has no mesh check; add `assert` product over ATTN_DATA/BATCH axes == 1 or fall back to the default path.

**4. MEDIUM — kernel at H_local=2: decode/mixed verified, prefill NOT verifiable off-TPU; the kernel's own CPU-interpret shim is broken for the prefill case.**
Ran the real `mla/v2` kernel via its `_INTERPRET` path (fp32, kv_packing=1) at H=2 with the exact v4 config ((1,1,1)/(1,8,8), decode_batch_size=4, s_dtype=f32), probes in `/tmp/claude-2001/-home-gianl/8712a40e-7bbe-436d-b0ad-d676cbd502d5/scratchpad/{interp_h2,interp_ab,interp_stale}.py`:
- No shape/min-row assert fires at H_local=2 (padding is `align_to(H, dtype_packing)` — 2 is legal; row asserts are `% num_q_heads`/`% bq_sz`, kernel.py:425-427,529-531).
- Decode (batched, 4-deep) and mixed-case outputs AND cache writes are **bit-exact** vs a contract reference at H=2.
- The pure-prefill case is wrong under `_INTERPRET` at **every** H tested (2, 8, 64): the prefill sequence's new-KV cache writes are garbage (max err ~5.7 on unit-normal data) and outputs match neither fresh nor stale cache; the same sequence classified as mixed is bit-exact. Since it is H-independent and on-TPU dense prefill passed parity/gsm8k at H=64, this is a bug in the `_INTERPRET` shim (introduced in f05abafa, likely the prefill-case bkv fetch/write reformulation around kernel.py:1470-1479), not an H=2 defect — but it means (a) prefill at H_local=2 has NO off-TPU evidence, and (b) any future CPU test trusting `_INTERPRET` for prefill validates garbage. Fix the shim; A/B prefill on TPU (gate on vs off) before enabling GLM_MLA_HEAD_SHARDED.

**5. MEDIUM — "q is born P(ATTN_HEAD)" is a propagation hope, not a contract; perf claim unverified.**
`attention_interface.py:534-536` / commit message. Correctness never depends on it (jit reshards inputs into shard_map specs). The perf claim is plausible: `W_UK_T` is explicitly `device_put` with `P(ATTN_HEAD,)` (mla_attention.py:230-233) and the head-sharded in_spec is a consumer-side constraint, so GSPMD propagation should keep the `"bnp,npl->nbl"` einsum output (flash_attn_mla.py:173-179) head-sharded through the scale-mul/astype (and the optional fp8 q quantization). But einsum output sharding absent an explicit constraint is a heuristic choice — GSPMD may materialize differently in the full-model context. Needs on-TPU HLO dump at TP-32: count collectives between that einsum and the shard_map custom-call (expect zero with the gate on, one head→token reshard with it off). Cheap belt-and-braces: `with_sharding_constraint(q_nope, P(ATTN_HEAD, None, None))` before the call.

**6. LOW — "The adapter is a few trace-time views/transposes — XLA folds them" (mla_attention.py:456-459) is wrong at runtime.**
Weights are jitted-function inputs; the fp8→f32 casts execute EVERY step: wq_b [2048×4096] + fused [160×6144] per full layer × 22 layers ≈ 0.75 GB/step of extra HBM traffic (more once finding 1's dequant is added). Per-call rebuild is the right call for tracer hygiene, but the honest fix is precomputing dequantized JAX params once in PWAL (device arrays, not traced values). Acceptable for a validation path; the comment will mislead upstream reviewers. Related documented cliff: `sparse_bias_from_indices` materializes [T, topk, S] bool — 8.6 GB at T=S=topk=2048, so "validation-scale" tops out well below the production topk.

**7. LOW — cross-host env divergence hazard for both gates.**
`GLM_MLA_HEAD_SHARDED` and `GLM_DSA_MODE` are raw `os.environ` reads at trace time inside per-layer code. glm_dsa_indexer.py:83-84 itself warns Ray only forwards `VLLM_*` to workers; v4-64 is 8 hosts — one host missing the env traces a different SPMD program (hang/garbage). The S1 commit carries no such warning. Upstream-grade fix: plumb through `tpu_inference/envs.py`/vllm config instead of ad-hoc env reads.

## Refuted / verified-clean
- **Fused split [:128]/[128:]**: correct. vLLM's `MergedColumnParallelLinear(hidden, [head_dim, n_head], disable_tp=True)` orders [wk | weights_proj]; head_dim=128, n_heads=32 (config: index_n_heads=32 — the deepseek_v2.py "# 64" comment is DSV3.2's value, port reads the attr). `_oriented`/transpose heuristic is safe: 160×6144 and 4096×2048 are non-square and 160≠6144 collision-free; the post-PWAL [in,out] transposition is handled.
- **wk_weights_proj values**: safe — `quant_config=None` + `_try_load_fp8_indexer_wk` dequantizes fp8 wk to bf16 at load; `weights_proj`/`k_norm` are in modules_to_not_convert.
- **RoPE**: verified against vLLM — indexer rope is plain `RotaryEmbedding` (config rope_type "default", theta 8e6, `.base` and `.is_neox_style` exist), `is_neox_style = not indexer_rope_interleave(True)` → interleaved; inv_freq formula and gptj-style pair rotation match the port. (The `float(getattr(indexer.config, "rope_theta"))` fallback would crash on GLM-5.2 — top-level rope_theta is None, it lives in rope_parameters — but the primary path always fires since the wrapper passes `indexer_rope_emb`.)
- **k_norm**: vLLM `LayerNorm` has `.weight/.bias/.eps`, fp32, biased variance via `F.layer_norm` — port math matches; not quantized.
- **Scale placement pre- vs post-relu**: bit-equivalent (positive scale), fine.
- **IndexShare carriage**: fresh `VllmModelWrapperContext` per model call (vllm_model_wrapper.py:652/713/1025/1053, `default_factory=dict`) — no cross-step leakage; first-layer-shared misfire raises loudly; wrapper patch (`_maybe_patch_for_glm_moe_dsa`) nulls the Indexer on shared layers consistently with `is_full_layer`.
- **S1 default path byte-identity**: in_specs/out_specs and `_gather_tokens` reduce exactly to the old expressions with the gate off.
- **k/k_rope-replicated cache-write consistency (5)**: confirmed at source level — `_update_kv_cache` DMAs are driven only by kv_lens/cu_q_lens/page_indices/distribution (all replicated) and the replicated new_kv buffers; no q-content or head-count dependence in the write path; interpret run showed identical decode/mixed writes at H=2. Caveat: `check_vma=False` means a violation would be silent, and the prefill case is only arguable on-TPU (finding 4).
- **W_UK_T/W_UV dequant in the xla_ref oracle**: scale shapes/axes handled correctly ([H,1,L] broadcast; W_UV_scale swapaxes to [H,1,V]); identity scales when kv cache unquantized.
