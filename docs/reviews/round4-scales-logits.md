== ATTACKED CLAIMS THAT SURVIVED (refutations, with evidence) ==

R1. Attack 1 (scale reorder != weight reorder) — REFUTED, proven safe.
`reorder_concatenated_tensor_for_sharding` (tpu_inference/layers/common/utils.py:28) is pure slice_in_dim/reshape/concat; the permutation depends only on (split_sizes, n_shards, dim, axis length). No dtype-, value-, or rank-dependent branch. Weight reorder (process_linear_weights, linear_weights.py:119, dim=-1 which normalizes to 1 for 2D) and scale reorder (fp8.py:205, dim=1) pass identical output_sizes/n_shards, and the full-res scale has the identical axis-1 length — same permutation by construction. CPU check T1: per-shard dequant after reorder is BIT-EXACT equal to the per-part dequant reference, including a ragged last fused part (the kv_a_proj_with_mqa 576-at-block-128 analogue) with per-shard width smaller than the block (the q_a 2048/32=64 situation). A part size not divisible by n_shards fails loudly in the reshape (n_shards, -1), never silently.

R2. Attack 2 (mixed K-expanded + N-block-granular in xla_quantized_matmul) — REFUTED as a live bug.
Reachability: every producer of 2D scales into xla_quantized_matmul (layers/vllm/quantization/fp8.py:205, compressed_tensors_w8a8_fp8.py:160, layers/jax/quantization/fp8.py:283) goes through process_blockwise_fp8_linear_weights, which after b921293c emits FULL-RES N in both the fused and split branches — so `out_cols != out_features` (linear.py:65) is dead code for GLM; after 79a5c17d K expansion, in_blocks==in_features gives block_size=1 and the N branch is never entered. If the mixed case ever arose, it is LOUD: the linear.py:66 assert (ceil(out_features/1)==out_cols) fails at trace time; even with asserts stripped the [K,out_cols]x[K,out_features] broadcast fails (CPU check T3). CPU checks T2/T2b: K-expanded (16-blocks/32-shards analogue) and block-granular-divisible (o_proj analogue) shard-local dequants are bit-exact. GLM's quantized layer set contains no ragged K (all contracting dims are multiples of 128: 6144, 2048, 512, 12288, 16384, 2048), verified against /home/gianl/glm-tpu/reference/hf-repo/config.json.

R3. Sampling correctness over vocab-sharded logits (attack 3a) — no manual sharding code anywhere in the path: sample/gather_logprobs/log_softmax/top_k (sampling.py) are plain jax.jit consumed by the GSPMD partitioner, which guarantees layout-independent results; the only shard_map (_select_from_array_fn, tpu_runner.py:1928) selects rows, never the vocab axis. Greedy argmax is computed on the vocab-sharded array directly (sampling.py:128) — partitioner-correct.

R4. Serving-time live-compile/desync worry for the new layouts — REFUTED empirically for this config: zero XLA compiler activity in the entire serving window (06:41–07:02) of smoke16.log; all jit_sample (3 fingerprints), jit_convert_element_type (3), jit_compute_logits_func (2), select/gather variants compiled 06:39:48–06:40:27 during precompile. The KEYSTONE gather-block (compilation_manager.py:1284-1408) drives the REAL compute_logits_for_logprobs_fn/select/sample, so precompile layout tracks the 10efa393 change automatically.

== FINDINGS (most severe first) ==

1. MEDIUM-HIGH — prompt-logprobs path is one config knob away from re-opening the exact failure class these commits fixed; currently protected only by max_num_batched_tokens=512.
Files: tpu_inference/runner/tpu_runner.py:1928 and :1367-1377; tpu_inference/runner/compilation_manager.py:1265; tpu_inference/layers/jax/sample/sampling.py:166.
Scenario (a) HBM: with 10efa393, full_logits is vocab-sharded; but `_select_from_array_fn`'s shard_map in_spec P(ATTN_DATA) (all size-1 axes on GLM) forces the [num_tokens, vocab] logits to be resharded to vocab-REPLICATED per chip before row-select, and the gather's top_k over the vocab axis needs the same. At the current 512 bucket that is 512x154880x2B=151 MB bf16 (317 MB after the f32 cast) — fits, and it precompiled (jit_compute_and_gather_prompt_logprobs at 06:40:21 in smoke16.log). Raise max_num_batched_tokens to 4096 for benchmark throughput and it becomes 1.27 GiB bf16 / 2.54 GiB f32 per chip against the pod's reported 1.16-1.59 GB headroom -> RuntimeProgramAllocationFailure at startup precompile (loud, blocks bring-up). This is the DSV4-comment "involuntary full rematerialization" made reachable again on the pure-TP mesh.
Scenario (b) desync: compilation_manager.py:1265 skips the prompt-logprobs chain precompile for any num_tokens bucket not divisible by 32, justified by a DSV4 token-DP invariant ("runtime never produces indivisible num_tokens") that is FALSE on pure TP. Today moot (single 512 bucket via TPU_MIN_TOKEN_BUCKET); lower/remove TPU_MIN_TOKEN_BUCKET and the first prompt_logprobs request hitting a 16/48/... bucket live-compiles the gather chain staggered across 8 hosts — the documented worker-3 launch-group halt class. Note lm-eval loglikelihood-style tasks request prompt logprobs; the generation-only smoke never executed this path with real data.

2. MEDIUM — the lm_head "vocab-sharded" detection counts size-1 mesh axes as sharded; the "pure-DP byte-identical" commit claim is unproven and likely false.
File: tpu_inference/models/vllm/vllm_model_wrapper.py:966 (`lm_head_vocab_sharded = any(s is not None for s in spec)`).
Scenario: on a model==1 (pure-DP) mesh the lm_head is placed with P(MLP_TENSOR, None) (layers/vllm/quantization/unquantized.py:170) where MLP_TENSOR names size-1 axes; if NamedSharding.spec round-trips those names (not normalized away), detection returns True and 10efa393's `(model_parallel or logprobs_layout) and not lm_head_vocab_sharded` silently disables STEP-1's token-sharded prompt-logprobs layout on pure-DP — reinstating the ~5 GiB [tokens, vocab] materialization STEP 1 existed to fix. Harmless for the GLM pod (model=32), a regression for any DSV4/pure-DP redeploy of this shared fork. Fix: compute the product of the actual mesh sizes of the spec'd axes on the vocab dim (dim 0) only — the `_axis_shards` helper at linear_weights.py:206 already does exactly this. Also: the bare `except Exception: pass` at :967 silently falls back to the OOM-prone forced-token-sharded layout; failure would be loud (startup OOM) but undiagnosable.

3. LOW-MEDIUM — temperature>0 sampling is a compiled-but-never-executed surface with a scaling cliff.
File: tpu_inference/layers/jax/sample/sampling.py:119-126.
Scenario: do_sampling=True explicitly replicates the [padded_num_reqs, vocab] f32 logits on every chip (an all-gather from the vocab-sharded layout new to GLM) and runs topk_mask/topp_mask over the full 154880 vocab. At num_reqs=8 this is 5 MB (precompiled fine); at a production max_num_seqs=256 it is ~159 MB plus several mask temporaries per step (~0.5 GB transient) against ~1.2-1.6 GB free. Failure would be loud at precompile after the config change, but it will be attributed to "sampling" not to this constraint. The smoke (greedy) provides zero evidence about this path's behavior or numerics.

4. LOW — real, CPU-demonstrated silent-numerics trap in 79a5c17d, unreachable with GLM dims.
File: tpu_inference/layers/common/process_weights/linear_weights.py:226 (`block = -(-w.shape[i] // s.shape[i])`).
Scenario: for a RAGGED block-granular axis (dim not a multiple of the true quant block, e.g. K=4160 -> 33 scale rows), ceil division reconstructs block=127 instead of 128; CPU check T4 shows 528/4160 rows silently get the wrong scale — a genuinely silent mis-dequant. Unreachable today (all GLM quantized contracting dims are multiples of 128, and the N axis always arrives full-res), but nothing guards it: a future model (or MTP variant) with a non-128-multiple contraction dim silently serves mis-scaled numbers. Add `assert w.shape[i] % s.shape[i] == 0` before expanding, or derive the block from weight_block_size.

LOW — config-flip fragility: ENABLE_QUANTIZED_MATMUL_KERNEL=1 (default off, envs.py:274) turns these 2D scales 4D (format_linear_scale, linear_weights.py:95) and routes to gmm_v2; the 79a5c17d expansion lives only in the 2D branch, so shared_experts.down_proj re-hits the IndivisibleError (loud), and full-res-N rhs_scale semantics in the kernel are unvalidated.

== ATTACK 4: what 3/4 GSM8K actually proves ==
- Strongly refutes: every-token mis-scaling classes (attack 1/2 — wrong q_a/kv_a or shared-expert scaling at all 79 layers => incoherent output, ~0%), vocab-shard index-offset argmax bugs (~0%). Three coherent, correct multi-step solutions are incompatible with these; the math proofs above refute them independently.
- Refutes weakly or not at all: (i) a mis-scaled subset of the 256 routed experts (per-tile GMM dequant, commits 8ad980e7/4e24a6c6 — OUTSIDE this review's target set): 8/256 routing means a few bad experts could cost 5-30 GSM8K points while staying coherent — invisible at n=4; this is the largest un-refuted silent-numerics surface in the served numbers. (ii) bf16-fold rounding (0.3% rel, commit-claimed): ~0-2 points, systematic — indistinguishable. (iii) anything in do_sampling / logprobs / prompt_logprobs paths: never executed. (iv) n=4 binomial: 3/4 is consistent with true accuracy anywhere ~40-99%; worse, the single failure (gsm8k_2: extracted 150 vs gold 70000, gen_tok=512 == cap) looks like generation-length truncation, so the effective evidence is 3/3 unconstrained samples.
- Expected signatures if a bug were present: attack-1/2 class ~0% + gibberish; single-expert mis-scale: normal fluency, 5-30 point deficit, errors concentrated in arithmetic-heavy steps; logits-layout bug: exact-0 or shard-multiple token ids in output. Recommendation: n>=200 greedy GSM8K vs the published GLM-5.2 number (accept within ~3 points); a prompt_logprobs probe of a fixed string vs HF CPU reference (also exercises finding 1 while buckets are still 512-capped); one temperature>0 request.
