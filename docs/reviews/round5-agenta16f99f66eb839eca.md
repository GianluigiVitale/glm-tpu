# Adversarial review — Stage-2b `indexer_kernel.py` @ 34972e8a

## Findings

**1. MEDIUM — undeclared same-dtype requirement; production 2a feeds fp32 q against a bf16 k-cache** — `tpu_inference/kernels/dsa/indexer_kernel.py:159-165, 266-269`; `tpu_inference/layers/vllm/custom_ops/glm_dsa_indexer.py:332-345`.
`compute_indexer_queries` returns **fp32** q (docstring says so; `as_jax_f32` at :337) while the design doc pins the indexer k-cache to **bf16** (§"bf16, head 128"; keys cast to `k_cache.dtype` at glm_dsa_indexer.py:536). When 2b swaps `indexer_scores_pallas` in for the XLA core, the kernel body issues `lax.dot_general(q_f32, k_bf16)` — a mixed-dtype MXU dot that Mosaic on v4 may reject outright (interpret mode upcasts and hides it; no test covers mixed dtypes; `_check_scoring_shapes` checks shapes only). The XLA twin is also silently degraded in this config: `_score_precision(f32, bf16)` → `DEFAULT`, and XLA promotes k to f32 then runs an f32×f32 dot at DEFAULT = 1-pass bf16 truncation of *both* operands — the lowest-precision configuration of any dtype combination, undocumented. Failure scenario: 2b integration flips `use_pallas=True` with the 2a-produced fp32 q → Mosaic lowering error on TPU (or, if accepted, path-dependent numerics untested anywhere). Fix: `assert q.dtype == kv_cache.dtype` in both scorers + explicit `q.astype(kv_cache.dtype)` at the wrapper boundary; add a mixed-dtype test or ban the combination.

**2. MEDIUM (design-doc flag, as tasked) — gate S "selected-set exact" is unachievable for the production bf16 scoring path as currently defined** — `~/glm-tpu/docs/01-dsa-kernel-design.md:328-332`; `tests/kernels/test_dsa_indexer_kernel.py:110-128`.
Gate S is written as "TPU indexer vs torch HF-math reference ... **fp32**: 0 index mismatches modulo ties". Production scoring is bf16 (bf16 cache, DEFAULT precision). Measured churn (Gaussian inputs, H=32, D=128, seeds 7–10): bf16 vs fp32 top-2048 sets differ by **1–2 non-tie indices (0.05–0.10%)** at ctx 4K–16K; per-score bf16 perturbation median ≈6e-3, p99 ≈2.6e-2 (unit-variance scores), and **26–42 positions sit within the p99 noise band of the k-th score** — so worst-case adversarial churn is ~2% even though typical is ~0.1%. These are *not* exact ties (score gaps ~1e-2), so "modulo ties" does not absorb them: gate S in bf16 must be defined either (a) vs a bf16-scored HF reference with matched rounding, or (b) as a boundary-band criterion (mismatches only where |s − s_kth| ≤ ε, ε ≈ 2⁻⁸ relative to score scale). Note the tests already quietly deviate the same way: `_assert_topk_set_equiv` accepts mismatches within `atol=1e-4` of the k-th score, whereas the doc demands strict score *equality* at the boundary — right engineering call, but the doc and test disagree; amend the doc (S1 = fp32 algorithmic/exact-modulo-ties — achieved; S2 = production-bf16 with the band criterion).

**3. LOW-MED — Mosaic/v4 rejection risks in specs that interpret mode cannot exercise** (the task's enumeration) — `indexer_kernel.py:326-346`:
- **(a) `(1, H)=(1,32)` fp32 w tile used as a matmul LHS** (`dot_general((1,32),(32,128))`, kernel :272-275). The validated DSV4 precedent has small tiles (`(n_rows,1)` sink, `(1,n_rows,1)` pos — dsv4/kernel.py:377-378) but only in *elementwise* use; there is **no validated precedent for a 1-sublane, 32-lane matmul operand** in this repo. Highest-risk single spec. Fallback if rejected: broadcast-multiply `w[0,:,None] * s` + sublane reduction (no MXU needed for a [32,128] head-sum).
- **(b) `(1, page_size)` fp32 output tile** (:334) — 1-sublane stores; likely fine, unproven here.
- **(c)** the mixed-dtype dot of finding 1.
- **(d) the entire `interpret=False` branch (:336-340) has zero test coverage** — verified `pltpu.CompilerParams`/`PrefetchScalarGridSpec` exist in both jax 0.6.2 and vllm-env jax 0.10.1, so no API-name crash, but `dimension_semantics`, vmem_limit and the compiled pipeline are all first-run-on-TPU.
- **(e) SMEM scaling of the scalar-prefetch table**: `bt_flat` is `i32[R*max_blocks]` in SMEM — 256 KiB at R=64/128K-ctx (page 128), 1.6 MB at R=256. Identical idiom to DSV4 (kernel.py:371-372 confirmed) but DSV4 was validated at ≤12K ctx; unproven at GLM's max shapes. Must be on the on-TPU checklist with max-(R, max_blocks) config.
- **(f)** no guard that `page_size % 128 == 0` when `interpret=False` (tests use pages of 8/16 — CPU-only conveniences); a non-128 page on TPU fails or pads unexpectedly. One assert.

**4. LOW (perf, on-TPU) — invalid pages still DMA; the pad contract permits the worst case** — `indexer_kernel.py:41-44, 314-317`. `pl.when` skips MXU work only; Pallas fetches the mapped cache block every grid step, eliding only consecutive *identical* block indices. With constant pad ids (tests use page 0) waste is ~1 page/request; but the documented contract "any in-range page id" permits arbitrary garbage pads ⇒ full `max_blocks` streaming for every short request in a long-max batch. Tighten the contract to "a constant (or repeated) page id" or have `cache_map` return the request's last valid page for `b*page_size >= kv_len` (klen is available in the index map).

**5. LOW (hardening) — `n_valid` not clamped to the map width** — `indexer_kernel.py:411`. If a caller violates the documented `kv_lens <= max_blocks*page_size` contract, `n_valid = min(kv_len, topk)` can exceed the finite-score count when `S < topk`; slots `< n_valid` then hold −inf-pad positions ≥ S, which 2c's `gather_kv_segment` treats as valid (`safe_t // page_size ≥ max_blocks` → out-of-range `take_along_axis`). One-line fix: `jnp.minimum(kv_lens, min(topk, S))`… (with `topk ≤ S` in production this is theoretical; documented-contract violation, hence LOW).

**6. INFO — cross-agent note for the 2c glue**: `kv_len==0` padding requests yield `n_valid=0` → `seg_valid=0`, which is **out of `dsa_sparse_decode`'s contract** (`seg_valid >= 1`, sparse_mla_kernel.py:191); it degrades to output 0 (not NaN) via `_finalize`, but the glue layer must mask padding rows. Also 2c's justification comment "decode always selects at least the self token" is wrong as stated (the self token is *not* guaranteed in the top-k when ctx > topk; the true guarantee is `n_valid ≥ 1 ⇐ kv_len ≥ 1`) — the requirement holds, the comment's reasoning doesn't.

## Refutations / claims verified (attack attempts that FAILED)

- **Exact-hierarchical-top-k incl. tie ORDER: HOLDS.** ~2,500 adversarial checks, **0 failures**: mass relu-zero rows (mostly-0.0 with few positives/negatives), tie groups of equal values placed exactly astride merge-block boundaries with exactly k−1 strictly-greater values (boundary tie *is* the k-th rank), negative-value ties, quantized 7-value heavy-tie rows to 8K, signed-zero rows, `merge_block ∈ {1,2,3,7,16,100,128,k−1,k,k+1,S,S+13,None}`, `kv_len ∈ {0,1,k−1,k,k+1,…}`, `topk` up to row width. Full-array equality vs flat `lax.top_k` on the identically padded row, order included. The docstring's exactness proof is sound *including* tie semantics: for a flat-selected x, (#strictly-greater + #equal-with-lower-index) < k globally bounds the same counts within x's block, so x survives per-block `top_k(min(k, block))`; candidate order (block asc → index asc for equal values) makes the merge reproduce flat tie order.
- **`lax.top_k` tie order** confirmed lowest-index-first (`[1.,3.,3.,2.,3.]`→`idx [1,2,4,3]`). One sharp edge found and neutralized: the top-k total order **distinguishes −0.0 < +0.0** (measured: `[-0,+0,-0,+0]` → `idx [1,3,0,2]`). Not exploitable: a relu-zero score's sign is determined per-row by `w` (constant per request), both scoring paths produced bitwise-identical maps on CPU (verified incl. an all-negative-`w` case engineered for −0.0), and flat/hierarchical see the same array. Worth one docstring line at most.
- **−inf/validity contract at kv_len ∈ {0,1,topk−1,topk,topk+1}: HOLDS** in both paths (suite + my fuzz); garbage in the tail of the last valid page correctly per-position masked; kv_len=0 rows are all −1/n_valid=0.
- **2b→2c padding contracts MATCH — verified by composition, not just reading**: ran `dsa_topk_indexer` output straight into `gather_kv_segment` with a tagged latent cache: `seg_valid == n_valid` exactly; −1 is a strict tail suffix (first n_valid slots all ≥0, all < kv_len — guaranteed structurally because every valid position's index < every invalid position's index, so even −inf-tie pathologies can't leak an invalid index into the prefix under lowest-index tie-breaking); gathered rows are exactly the selected tokens. **The indexer emits indices in descending-score order, NOT position-sorted; the gather does not require sorted** (`indices_are_sorted=False`, attention permutation-invariant) — contract compatible, but the ordering should be stated in the design doc §3.1 since a future kernel exploiting index monotonicity would silently break.
- **Grid/BlockSpec index math vs the DSV4 idiom: faithful.** `cache_map` `bt[r*max_blocks + b]` matches dsv4/kernel.py:371-372 (plus a defensive clip DSV4 lacks — an improvement; note the clip path itself is untested since test pads are always in-range page 0); prefetch signature/order, `o_map (r,b)`×block `(1,page_size)` offsets, and the precision rule (dsv4:350-354) all check out. No off-by-one found at page boundaries (129/128/17/1-length cases + shuffled-table bit-invariance pass).
- **Overflow probe**: NaN scores require |q|,|k| ≈ 3e19 (fp32 q·k overflow) — unreachable post-norm activations; no guard needed, but note top-k order is poisoned if it ever happens.
- **Docstring arithmetic**: VMEM table (~161 KiB @P=128 fp32), 32 MiB score map @R=64/128K, grid 65,536 steps — all correct.
