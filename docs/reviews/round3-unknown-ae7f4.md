## Findings (most severe first)

**1. HIGH — real-tokenizer token-length targeting is off by −17.2%: the "128K" cell actually tests ~108K tokens, "1M" tests ~868K.**
`bench/glm_longctx.py:143-152` (`build_trial` sums per-sentence standalone token counts). Under the real BPE tokenizer, per-sentence counts are NOT additive: each filler sentence ends in a trailing space that tokenizes standalone as its own `Ġ` token but merges into the next sentence's first word (`ĠThe`) in context — every boundary loses exactly 1 token (5-sentence cycle: 29 standalone vs 24 in concatenation = 82.76%). Measured with the real tokenizer: L=131072 → **108,473** real prompt tokens (82.76%); L=1,048,576 → **867,789** (82.76%); constant at every L. Failure scenario: the Stage-2 gate line prints `L= 131072 ... [PASS @ the >=95% Stage-2 bar]` from a measurement taken at ~108K tokens — the "≥95% to ≥128K" threshold claim is misstated by −17% (a true 128K test needs `--lengths ~155k`). The mock whitespace tokenizer is exactly additive, so `test_token_length_targeting` (test_longctx.py:31-37, `L-8 <= n <= L`) structurally cannot catch this. Mitigation that exists: real `n_prompt_tokens` is recorded per item and `avg_prompt_tok` per cell, so the DB contains the truth — but the benchmark labels, JSON `lengths`, and the PASS/fail gate all key off the target L. The commit message's depth claim is accurate; `build_trial`'s docstring ("filler of ~target_len tokens") and the per-length gate reporting are not.

**2. HIGH — the documented `[gMASK]<sop>` prefix does not exist: `add_special_tokens=True` is a no-op for this tokenizer.**
`bench/glm_longctx.py:22-24` (docstring), `:184` (`make_raw_generate`), repeated in `docs/RESEARCH_LOG.md` ("Tokenized add_special_tokens=True ([gMASK]<sop>)"). Empirically refuted: the tokenizer's `post_processor` is plain `ByteLevel` (no special-token template); `tok("Hello world", add_special_tokens=True)` == `add_special_tokens=False` — zero tokens prepended. `[gMASK]<sop>` (ids 154822/154824) comes only from the chat template's literal first line (`chat_template.jinja:1`). Failure scenario: the raw-completion prompt is a bare BPE stream with no special tokens at all, while every GLM training/serving sequence starts `[gMASK]<sop>` — the protocol is more out-of-distribution than the harness believes, and the documented mitigation is factually wrong. If long-context retrieval fails on the pod, this misdocumented prompt shape is a candidate MODEL-side cause the docstring will steer debuggers away from. Fix is one line (prepend ids 154822, 154824, or prepend the text) plus doc correction.

For 1M: 1,048,576+256 = 1,048,832 > `max_position_embeddings` = 1,048,576 (verified in `reference/hf-repo/config.json`; `rope_scaling=None`). **4. MEDIUM — raw-completion protocol confound is real and only half-mitigated; the docstring's justification is incomplete.**
Attack (1) of the brief. GLM-5.2 is a thinking/chat post-trained model; no evidence in the repo that it reliably continues raw completions (unverifiable without a pod run — the commit honestly says none ran). Two specifics: (a) the docstring's dichotomy "chat template ends `<|assistant|><think>` → budget eaten by thinking" ignores that the template supports a **non-thinking chat mode** — `enable_thinking=False` renders `<|assistant|><think></think>` (`chat_template.jinja:118`) which would give a direct in-distribution answer; the raw-completion choice may still be right (canonical Mohtashami & Jaggi protocol) but the stated rationale omits the obvious alternative. (b) `<|assistant|>` (id 154828, verified) is NOT in `EOS_IDS` (engine.py:39), so the claim "a turn-taking continuation halts immediately" (glm_longctx.py:25) holds only for `<|user|>`/`<|observation|>`/`<|endoftext|>`; a generated `<|assistant|><think>…` burns the 20-token budget and scores wrong. Failure scenario: model-side protocol failure (off-template rambling, chat-token emission) produces 0% cells that the gate line reports as retrieval failure. Existing mitigations: short-L cells in the same ladder act as a de-facto control, and raw outputs are stored verbatim for audit — but nothing enforces "trust long-L only if short-L passes"; each per-length PASS line is independent.

**5. MEDIUM — no KV/HBM feasibility documentation for 128K–1M anywhere in the commit (attack 5).**
The RESEARCH_LOG entry, module docstring, and HANDOFF diff say nothing about KV at the advertised lengths. Arithmetic: MLA latent KV = (kv_lora_rank 512 + qk_rope 64) × 2 B (kv auto→bf16) × 78 layers ≈ 87.8 KiB/token → **~11 GiB @128K, ~88 GiB @1M per sequence**. Per-chip HBM ≈ 32 GiB with ~23.3 GiB FP8 weights resident → ~8.7 GiB free before the forward program. Feasibility hinges on whether tpu-inference shards the latent KV across TP=32 without DP-attention (the engine recipe explicitly drops `enable_dp_attention`, engine.py:7-9); if it is per-rank-replicated, even the 128K cell OOMs at engine build. The DSV4 per-rank-KV/DPScheduler lesson (moe-tpu docs/16) that CLAUDE.md names as the 1M bottleneck is not referenced. The commit does not overclaim (it says pod run is next-session), but a "Stage-2 threshold instrument to ≥128K" that cannot state whether its engine can hold 128K of KV is an undocumented cliff.

**6. LOW — extractor digit-grouping gaps.**
`bench/glm_longctx.py:163-174`. Verified robust: leading spaces (regex `\d+`), thousands-commas (stripped), unclosed `<think>` within 20 tokens (digits still extracted), no truncation/guessing (test-verified). Not handled: space-grouped ("483 920") or dot-grouped ("483.920") answers → only 3-digit runs → `None` → scored wrong and misattributed to attention. Probability is low (greedy copy of an ungrouped needle; ` 483920.` = 6 tokens, well under the 20 budget — measured), and the raw output is stored, so it is auditable.

## Claims I tried to refute and could NOT (verified true)

- **Depth ±2% with the REAL tokenizer** — holds, strongly: measured needle-fraction error ≤ **0.4pp** across L∈{1K,4K,32K,128K} × d∈{0.1,0.25,0.5,0.75,0.9} (boundary merges deflate numerator and denominator uniformly, so the fraction is preserved even though the length is not).
- **Needle exactly once / always 6 digits** — filler and cue are digit-free by construction; `rng.randint(100000, 1000000)` is high-exclusive; `ctx.count(key)==1` holds with the real build; prompt ends with the cue.
- **EOS ids** — `[154820, 154827, 154829]` match `generation_config.json` exactly and decode to `<|endoftext|>`/`<|user|>`/`<|observation|>` in the real tokenizer.json (the *names* in the comment are correct; only the `[gMASK]<sop>` claim was false).
- **Refactor behavior-identity (attack 4)** — the `LLM(...)` kwargs block in `engine.build_llm` is **byte-identical** to the pre-refactor block in `run_bench.make_generate` (programmatic diff of `5c79e1c^:bench/run_bench.py` vs `bench/engine.py`: True); the log line is byte-identical via `log_extra`; `DEFAULT_MODEL`/`EOS_IDS` re-exported. `run_bench --stub` executed end-to-end (gsm8k, limit 2, DB redirected to scratchpad): completes, records 2 items, and `"vllm" not in sys.modules` — the vllm-free claim is empirically true for both harnesses. `test_longctx.py` 9/9 and `test_bench.py` all-green re-confirmed by me.
- **Provenance (attack 3)** — reconstruction works as claimed *given the same tokenizer*: `build_trial` is deterministic in (tok, L, d, seed) (numpy `RandomState` is version-stable), seed is stored per item, L/d recoverable from the benchmark name, sha256 lets a rebuild be verified; raw output is always verbatim. Caveats: the tokenizer is not content-pinned (`--revision` defaults to None/NULL, the model path is a mutable GCS prefix, no tokenizer hash stored) — the stored sha256 can detect but not repair a drifted rebuild; the summary `.json`/`.jsonl` files are overwritten per run (only the DB appends). "1M builds in 0.21 s" — I measured 0.10 s; plausible.
