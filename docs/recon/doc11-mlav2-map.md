# mla.v2 kernel structural map (from `~/moe-tpu/docs/11-mlav2-kernel-structural-map.md` + source spot-checks)

## 1. Files + call graph
- Kernel: `tpu_inference/kernels/mla/v2/kernel.py` (2609 lines) + `tuned_params.py`; helpers `kv_utils.py`, `transpose.py` (doc:5, dir listing).
- Attention layer → kernel: `tpu_inference/layers/common/attention_interface.py:33` imports `mla_ragged_paged_attention`; `_mla_ragged_paged_attention` wrapper at `attention_interface.py:546` calls the kernel at `:565`, wrapped in `jax.shard_map` at `:584` — the MLA backend's DP recipe (attention_interface.py:526-591; doc:74-76): cache `P(BATCH)`, metadata `P(ATTN_DATA)`, weights/rope replicated, block_tables hold per-rank-LOCAL page ids.
- Kernel entry `mla_ragged_paged_attention` at kernel.py:2171; the pallas builder is kernel.py:2340-2532, kernel body 298-2030 (doc:32). Grid is **1D over sequence batches** `((end_seq-start_seq)//batch_size,)` (kernel.py:2373); query blocks (`bq_idx`) and KV blocks (`bkv_idx`) are `fori_loop`s **inside** the kernel, not grid axes; `bkv_sz = num_kv_pages_per_block * page_size` (doc:33-35). Double-buffered VMEM (`*_x2` refs, semaphore 0/1) for KV (`bkvc_x2`/`bkpe_x2`), q, output, plus flash accumulators `l/m/acc` (kernel.py:2391-2425; doc:36-38). DMA walks `page_indices` HBM→VMEM (doc:39-40). Output is head-major `[H,T,lkv]` via `prepare_outputs` (kernel.py:2145,2205); the kernel emits the **attended latent** — W_UV/o-proj stay post-kernel in XLA (doc:28-30).

## 2. FP8→bf16 dequant hook
- `_upcast_kv_for_v4` gate at kernel.py:358-359: `device_kind == "TPU v4" and bitwidth(kv_dtype) < 16` — v4's MXU has no fp8 matmul path (comment at 354-357). Applied at three sites: whole-block KV upcast at 437-439; the **narrow per-256-chunk transient upcast** inside the QK loop at 571-575 ("transient bf16, freed after the matmul, so peak VMEM stays within v4's 16 MiB"); and the concat-path upcast at 593-594. PV also upcasts at ~669 (doc:58-60). Note this is *scale-free* fp8 KV upcast — GLM's FP8 **weight** tile dequant (128×128 block scales) is upstream of the kernel; only if an fp8 KV cache with block scales is kept would a scale multiply need to be added at these three sites.

## 3. v4-specific block sizes / workarounds
- `_xpose_tiles` (kernel.py:36-45): transpose tiles shrunk 128×32→64×16 on v4 (q_nope transpose needs ~24.45 MiB > v4's 16 MiB VMEM); called for q-prep/output-finalize xpose pipelines at kernel.py:2080, 2133 (doc:56-57).
- fp32 softmax path: QK/PV einsums all use `preferred_element_type=jnp.float32` (kernel.py:579,584,599,679); `exp`/`exp_m_diff` recurrence in fp32 (647-649); `l/m` scratch allocated fp32 (2429,2435); `TuningKey.s_dtype` defaults bf16 post-QK but scores are accumulated fp32 (tuned_params.py:35).
- Tuning: `TuningKey(case, max_num_tokens, actual_num_q_heads, actual_lkv_dim, actual_r_dim, kv_dtype, …)` → `TunableParams(decode_batch_size, num_kv_pages_per_block, num_queries_per_block, vmem_limit_bytes)` (tuned_params.py:23-56). Existing entries are **fixed at 128 heads / lkv 512 / r 64 / fp8** (comments tuned_params.py:26-29). On v4 tune `num_kv_pages_per_block` DOWN; unknown keys need a new entry or a logged sane default (doc:41-44, 61-63).
- Online softmax: standard `(m,l,acc)` recurrence with `exp_m_diff` computed once/block; masking uses ABSOLUTE KV positions; `two_step_flash_attention` variant decouples QK-softmax from PV with a one-block lag + final PV (~1902-1912). mla.v2 has **no per-head sink, no inverse-RoPE-on-output** (doc:47-53) — those were DSV4-only deltas.

## 4. Shapes assumed vs GLM MLA dims
- I/O contract (kernel.py:146-151,308-315): `ql_nope [T,H,lkv]`, `q_pe [T,H,r]`, `new_kv_c [T,lkv]`, `new_k_pe [T,r]`; packed cache `[pages, page_size//kv_packing, kv_packing, align(lkv+r,128)]` with lkv/rope as separate contiguous blocks, NOT interleaved (doc:17-21); `kv_packing = 32//dtype_bits` (doc:19); lkv/r each aligned to 128 (kernel.py:211-212) with `lkv+r == aligned_kv_dim` checked (231-233); `page_size % 128 == 0` (104).
- **GLM fit**: in the absorbed MLA decode form the kernel operates on the *latent*, so GLM's per-head dims mostly stay outside it: `kv_lora_rank=512 → lkv=512` and `rope 64 → r=64` are **exactly the DeepSeek dims mla.v2 is tuned for** (128-aligned; r pads 64→128). `q_lora_rank=2048` affects only the upstream q down/up projections. `qk_nope=192` enters only via W_UK absorption: `q_nope [T,H,192] @ W_UK[H,192,512] → ql_nope [T,H,512]` — kernel-invisible. `v_head_dim=256` enters only post-kernel: attended latent `[H,T,512] @ W_UV[H,512,256]` (mla.v2 already keeps W_UV post-kernel, doc:28-29). The one real dim change is **64 q-heads vs the tuned 128** (tuned_params.py:26) → new `TuningKey` entries (and re-check `bq_sz*H` accumulator sizing, `acc_ref [batch, bq_sz*num_q_heads, lkv]` kernel.py:325). Unlike DSV4 (full-latent K==V, sink, inverse-RoPE forced a purpose-built kernel), **GLM's MLA is the native mla.v2 contract** — no math deltas needed for the dense path. What mla.v2 does NOT provide is DSA sparsity: it attends the full ragged paged history; GLM's indexer top-k=2048 selection would need either a compacted/gathered page-indices LUT per query (fits the existing `page_indices` indirection) or an additive-bias/mask extension — the DSV4 pattern of feeding a precomputed appended segment + bias (doc:82-85) is the proven analogue.
