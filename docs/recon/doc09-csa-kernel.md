# docs/09 — DSV4 Pallas paged-decode plan (PR-A rock b): summary

**Context:** docs/09 is the SCOPED plan (`docs/09:3`); the kernel was subsequently built with one deliberate departure — a clean purpose-built kernel on the repo's `kernels/flash_attention` structure rather than an mla.v2 copy (mla.v2's PV is kv_c-only + post-kernel W_UV, no sink, no inverse-rope, and asserts latent/rope %128 which DSV4's 512=448+64 fails). Both plan and as-built are covered below.

## 1. Kernel design

**Why a kernel:** the XLA decode references (`_paged_decode_jit`/`_compressed_decode_jit`) materialize a per-token `[T, max_ctx, head_dim]` history gather and recompute all compressed entries from full cached projection history per step — OOM at production scale and TP=1-only (`docs/09:8-14`).

**Scaffolding/grid (plan):** copy mla.v2's ragged-paged scaffolding verbatim — grid `((end-start)//batch_size,)` (mla/v2/kernel.py ~2373), double-buffered DMA fetch/wait + `SemaphoreType.DMA((4,batch_size,2))` (~2445), the page-index + `cu_q_lens` walker, the v4 VMEM transpose cap `_xpose_tiles`, and the v4 fp8→bf16 upcast hook (`docs/09:28-31`). **As-built:** standard Pallas paged BlockSpec — scalar-prefetched block table → cache index_map, one physical page per (seq, kv-block) grid step; online-softmax scratch `(m,l,acc)` reset at kv==0, finalize at last block; the `[bq,H]→[bq*H,1]` row fold done in XLA host-side (Mosaic can't relayout).

**Four DSV4 math deltas** (`docs/09:33-43`): (a) PV over the FULL latent K==V (concat nope+rope), not kv_c-only; (b) per-head sink folded into the FINAL `(m,l)` ONLY — `m=max(running_max,sink)`, `l+=exp(sink-m)` once at finalize (per-block application double-counts, flagged the #1 bug risk, `docs/09:38-39,106`); (c) inverse-RoPE on output at query positions (`-sin_half`) AFTER `acc/l` normalization (`docs/09:40-41,107-108`); (d) grouped low-rank o-proj stays in XLA post-kernel — kernel emits attended full-latent `[N,T,head_dim]` (`docs/09:42-43,111`).

**comp_bias masking — how dynamic sparsity is avoided** (`docs/09:83-88,109-110`): the per-step compressed-entry recompute and indexer top-k stay in XLA as a deterministic PRE-STEP (`_hca_combine`/`_csa_overlap_combine` + indexer top-k); XLA materializes a fixed-shape, already-RoPEd `comp_kv [R,max_win,hd]` + additive `comp_bias` (0/-inf encoding window-causality/top-k selection). The kernel then does one fused dense flash over `concat(local paged | appended compressed)` — no re-rope, no causal mask on the segment, no top-k gather or dynamic indexing inside Pallas. Sparsity is expressed as an additive bias over dense fixed shapes. The later `DSV4_DECODE_COMP_BLOCK` tiling (kernel.py:202) flash-accumulates the compressed segment in tiles (comp_kv host-reshaped 4-D `[R,n_blocks,comp_block,hd]`, comp_block a multiple of 128) into the SAME `(m,l,acc)`, making VMEM independent of `max_win`.

**DP mechanism** (`docs/09:45-62`): wrap in `jax.jit(jax.shard_map(..., check_vma=False))` mirroring `attention_interface.py:526-591`; q/metadata/output `P(ATTN_DATA)`, cache `P(BATCH)` (same mesh axes); block_tables hold per-rank-LOCAL ids (dp_scheduler.py:515 allocates `num_blocks//dp_size` per rank; tpu_runner.py:2437-2448 copies with no rebasing) so `cache_local[block_id]` indexes correctly with no rebasing.

## 3. GLM DSA adaptation

**Adapts directly:** (a) the *sparsity-as-additive-bias over a dense appended segment* pattern is exactly what a top-k=2048 sparse-MLA decode needs — gather the indexer-selected 2048 tokens in XLA into a fixed `[R,2048,576]` segment (2048=16×128 tiles cleanly through the tiled compressed path) with bias 0/-inf, or bias-mask the full paged KV; either way no dynamic top-k gather in Pallas. (b) The online-softmax core, paged BlockSpec + local-block-id DP shard_map (cache `P(BATCH)`, metadata `P(ATTN_DATA)`), the bq*H head fold (GLM also 64 heads), and the VMEM tiling discipline. (c) Full-latent shared-KV MQA: GLM's 576-wide latent (512+64 rope) is the same shape class as DSV4's 512 (448+64) — same non-%128-rope issue that ruled out mla.v2.

**DSV4-specific (drop for GLM):** the per-head attention sink in the final `(m,l)`; inverse-RoPE on output; the sliding_window=128 local band; the HCA/CSA window-compression recompute pre-step (`_hca_combine`, coff=2 Ca/Cb look-back, `docs/09:110`). GLM's PV differs: standard MLA accumulates over kv_c (512, nope-only) + post-kernel W_UV to v_head_dim=256 — mla.v2's pattern, not DSV4's full-latent-out — so the PV/output stage needs GLM-specific math; the GLM lightning indexer (32 heads, hd 128, interleaved RoPE, IndexShare) replaces the CSA indexer in the XLA pre-step.

## 4. Validation methodology (`docs/09:75-91` + as-built results)

Increment ladder, each vs the rock-(a) XLA oracle: **(i)** dense TP=1 BIT-FOR-BIT vs `_paged_decode_jit`, harness modeled on `parity/dsv4_paged_decode_parity.py` — chunk patterns {one-shot prefill; prefill+1-tok; 1-by-1}, shuffled block table, tol fp32 ~2e-5 / bf16 ~6e-2 (`docs/09:76-80`); as-built achieved fp32 ~3e-8 / **bf16 0.0 bit-identical**, plus a real-dim smoke (head_dim 512, 64 heads, pages up to 1024, VMEM fits). **(ii)** TP=4==TP=1 identical generated tokens via `dsv4_runner_decode_parity.py` (`docs/09:81-82`); as-built 4/4 bit-identical. **(iii)** compressed via the appended segment; as-built standalone fp32 ~4e-8 / bf16 5e-5–2.7e-4, in-engine HCA/CSA tokens bit-identical to XLA baseline. **(iv)** 32-chip generation behind `DSV4_PALLAS_DECODE` (`docs/09:89-91`); gate = self-consistency + fp32 tracking (bf16-ref informational, MoE routing-flip floor documented). Microbench: 1.4x@512 → 4.3x@8192 ctx vs XLA blocked core.
