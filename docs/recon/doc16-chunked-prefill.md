## 1. Chunked-prefill cross-chunk attention bug + DSV4_DECODE_CACHE fix
- **Bug:** DSV4's default prefill path (`_paged_forward` / `_compressed_prefill_jit` → `_mqa_attend_blocked`, `DSV4_DECODE_CACHE` OFF) attends over the **current chunk's tokens only** — no read of cross-chunk cached KV history. When `max_num_batched_tokens < prompt_len` splits a prompt, every chunk after the first loses prior-chunk context (docs/16:7-12). `_paged_forward` docstring (deepseek_v4_attention.py:1700-1709) states exactness only for `context_len==0`; the mask is over in-batch `kv` from the current chunk only; the history-reading path `dsv4_paged_dense_mqa` was wired ONLY into `_paged_decode_jit` gated on `DSV4_DECODE_CACHE` (docs/16:15-21). Mesh-independent (pure-DP ≡ head-TP, mean diff 2.67/2.68); break = the first ~window positions after each chunk boundary (docs/16:22-27). MMLU corrupts iff the last chunk < window(128): mbt=256 → ~60, mbt=32 → ~25, non-chunked → ~88.7 (docs/16:28-32).
- **Fix B (production, no new code):** `DSV4_DECODE_CACHE=1` — `_paged_forward:1728` routes dense prefill through `_paged_decode_jit` (writes chunk KV to latent cache + attends `[0, seq_len)`); `_compressed_paged_forward:2381` routes compressed prefill through `_compressed_decode_jit` (recomputes compressed entries from cached history) (docs/16:45-52). Sub-cube validated all 3 modes (dense 0.18 vs 2.67; final position bit-identical) (docs/16:54-57). Preferred over non-chunked Fix A: small mbt-256 forwards fit HBM, no skips, enables true long context (docs/16:59-65). Powers 100% passkey retrieval 1K-4K (72/72) (docs/16:95-97).
- **Follow-on VMEM wall (LATEST-8/9):** `comp_kv [R, max_win, head_dim]` loaded un-tiled (`in_specs[4]`, kernel.py:325); `max_win ≈ seq_len/compress_ratio` scales with context → VMEM OOM ~12-16K (docs/16:99-112). Fixed by tiling: `_dsv4_decode_compressed_tiled_kernel`, gated `DSV4_DECODE_COMP_BLOCK` (mult of 128; comp_kv host-reshaped to 4D; host-pad, no in-kernel relayout) (docs/16:127-153); pod-validated max_len 33024, 0 VMEM OOM (docs/16:170-174).

## 2. Per-rank KV sizing / DPScheduler starvation fix
- **Root cause:** the custom `DPScheduler` (`tpu_inference/core/sched/dp_scheduler.py`, active iff `total_dp_size>=2`) pins each request to one DP rank for life (line 377) and gives each rank only `num_gpu_blocks // dp_size` blocks (`_create_per_rank_configs`, line 515), `block_size=1024`. A request needing more blocks than its rank holds can never allocate → 0 scheduled tokens/step → engine spins forever (`tpu_runner.py:1237`, "Should not schedule a request that does nothing!"). At 64 blocks / dp_size 8 = 8192-token cap; 8192-token prompt (9 blocks) wedges. No admission check (docs/16:183-191).
- **Layer 1** (`bench/dsv4_bench.py`): `build_llm` auto-raises `--num-gpu-blocks` to `required_kv_blocks(max_len, dp_size, max_seqs) = dp_size * ceil((max_len+1)/1024) * max_seqs`; additive; pod 64→136; `bench/test_kv_sizing.py` 5/5 (docs/16:194-196).
- **Layer 2** (fork `dp_scheduler.py`): `min_blocks_for_max_model_len` + startup `_warn_if_per_rank_kv_insufficient` — loud failure with remedy; `tests/core/test_dp_scheduler.py::TestMinBlocksForMaxModelLen` 4/4 (docs/16:197-199).
- **Pod results:** 100% retrieval 8K/12K/16K (model=4, 136 blocks) and 16K/32K (model=8/attn_dp=4, 132 blocks — halves per-rank block need + frees ~1.4 GiB weight HBM; `o_groups=8` caps head-TP at model≤8) (docs/16:201-210).

## 4. GLM applicability (1M context)
- **Applies directly:** (a) the chunked-prefill principle — any GLM prefill path MUST read cached cross-chunk history from step one (build the DECODE_CACHE-style unified write+attend path as default, not gated); (b) the `required_kv_blocks` formula + DPScheduler Layer-2 warning — scheduler-level, model-agnostic; at 1M context per-rank starvation is guaranteed without it (1M tokens ≈ 977 blocks/rank at block_size 1024); (c) the Pallas tiling discipline (4D leading-block-axis reshape, 128-multiple tiles, host-pad no relayout, online flash accumulation) for any window/KV structure scaling with context.
- **Needs rework:** GLM has no HCA/CSA compressor — `comp_kv`/`comp_bias` tiling doesn't transfer as-is. The analogous VMEM-scaling operand is the **DSA indexer** (topk=2048 selected positions, 32 heads × head_dim 128): the top-2048 selected-KV gather and the indexer's full-history scoring pass both scale with context and need the same paged/tiled treatment. MLA latent (kv_lora_rank 512 + rope 64 = 576 vs DSV4's 512) fits the dense paged path with dim changes. IndexShare-every-4-layers caching and MTP have no DSV4 precedent. At 1M, `ceil((max_len+1)/1024)` per-rank sizing implies the KV pool itself dominates HBM — the formula holds but block accounting must include the indexer KV cache.
