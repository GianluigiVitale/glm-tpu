Research outside `MODEL_SOURCE=edecdd94`; no serving default is replaced.

## D4 compact request loop

`glm_tpu/perf/request_loop.py` wraps the existing challenger in an outer JIT.
A request's original SHA256/24-bit FP32 uniforms are placed once, including
index 0 for prefill. Each decode selects `state.position - prompt_length + 1`.
The wrapper returns the original model result plus an int32 vector containing
token, all-owner health, next position and context length. Out-of-range draw
indices and nonfinite/out-of-range uniforms make compact health false.

`PackedRequestSession` retains the original prefill, stop, pause/resume and
release behavior. Decode reads the compact vector once, combines timing and
state admission into one fleet vote, commits the state/token before delivery,
and performs the existing delivery-success vote. It performs two votes per
decode token instead of three and no per-token uniform `device_put`. A failed
or ambiguous delivery still poisons the session and cannot emit a retry. The
callback must be the corresponding packed program with the same request's bank
and prompt length bound; arbitrary metadata is not an independent state proof.

Sixteen CPU tests passed in 55.40 s. They cover complete CPU32 model-output
bitwise equality, correct RNG index progression, invalid index/NaN refusal,
all-owner health propagation, local/remote refusal, clock failures, delivery
failure after commit, EOS/length stopping, pause/resume and boundary-call
counts. CPU proof does not replace TPU composition or timing evidence.

The completed TPU comparison uses the same sampled D1/D8/D5/D10 model, synthetic
weights and deterministic draws in both loops. Both perform real eight-host
votes and append events to an in-memory sink. Timing excludes compilation and
five warm steps; it includes all per-token host boundaries. Token trails, final
state/residual bit patterns and actual votes/transfers are compared. This is
not a network or filesystem delivery-latency measurement.

All eight ranks agree on all 106 recorded synthetic token IDs and byte-identical
final decoder state plus residual. Both sessions finish by length, healthy.
One hundred timed steps per variant give:

| Host loop | Wall tok/s | Step p50 | Step p99 | Model p50 | Votes / uniform transfers |
|---|---:|---:|---:|---:|---:|
| Original | 14.1088–14.1089 | 70.714–70.739 ms | 75.343–75.467 ms | 64.521–64.553 ms | 300 / 100 |
| Compact | 14.7137–14.7138 | 67.855–67.885 ms | 72.385–73.593 ms | 64.444–64.498 ms | 200 / 0 |

This is a **4.29% sampled wall-throughput gain**, about 2.9 ms/token, with the
same model and draw sequence. Both use an artificial 64-token zero-cache prefix;
no trained prompt, real delivery sink or frozen-sampler comparison is implied.
Temporary executable bytes increase by 512, from 252,412,928 to 252,413,440.
[Eight-rank receipt](tpu-microbench-request-loop-20260919T153427Z.json).

The trained-weight D1/D8/D10 repeat now passes all 29 DB610 IDs in both loops
on every host, with bitwise-identical final state/residual and finite caches.
Legacy **13.3195–13.3196** becomes packed **14.0446–14.0451 wall tok/s (+5.44%)**;
p50 falls from 74.958–74.996 to 71.319–71.367 ms. This is 23 timed steps after
five warm steps, including real host votes and an in-memory sink, excluding
transport. All eight hosts clean up. See the
[receipt](tpu-real-request-loop-20260919T192804Z.json) and
[source/timing scope](REAL_WEIGHT_VALIDATION_20260919.md#d4-trained-weight-host-loop-comparison).

## P4 wider output panels

`wide_prefill_panel_fp8_matmul` mirrors the frozen routed panel kernel with
N256/N512 output tiles. M32 panel packing and increasing K128 reduction order
are unchanged; every N128 stripe has its own FP32 accumulator and scale row.
The default prefill builder still uses the frozen N256 kernel.

Six CPU cases passed in 8.34 s, covering FP32/BF16 outputs, empty owners and
skewed panels, with bitwise equality at N256 and N512. The completed TPU experiment
includes packing/unpacking at real gate `[32,2048,1536]` and down
`[32,1536,2048]` local weight geometry, with balanced and concentrated routes.
Each output exposes both owner axes so feature-partial values are never
incorrectly declared replicas. All 32 chips report finite, healthy, bitwise-equal
results for the frozen kernel and both challenger tile widths, 30 samples each.

| Projection/routes | Frozen N256 p50 | Challenger N512 p50 |
|---|---:|---:|
| Gate / balanced | 2.536–2.545 ms | 2.525–2.532 ms |
| Gate / concentrated | 0.894–0.905 ms | 0.900–0.911 ms |

## Bounded owner attention buffers

The gathered LSE primitive has an opt-in `owned_key_capacity` parameter. It
canonicalizes each owner's selected positions once and uses a smaller buffer
only when every row's owned count fits. Otherwise that owner takes the original
full-width path. Branches contain no collectives; every owner reaches the same
LSE merge. Both branches retain the frozen gather's page, causal, duplicate and
padding guards. The kernel's segment width and increasing-key reduction order
are unchanged; this removes unused cache gather slots and Pallas grid iterations.
The full top-K buffer remains the default.

CPU8 proofs at M1/M3 compare all output, LSE and health bit patterns for empty,
single, balanced, random and concentrated selections, including mixed empty
rows and per-owner fallback. Duplicate positions and selected NaNs fail health;
unselected NaNs do not. Together with the D4, P4 and BF16 binding regressions,
**28 tests passed in 83.76 s**. The queued TPU comparison uses M32, top-K 2,048,
capacity 131,072 and a 512-key bound, including balanced, concentrated and mixed
selections. The first TPU attempt stopped in the host comparison before timing:
NumPy refused a byte view of a non-contiguous returned shard. All eight workers
exited and authenticated cleanup passed. The checker now makes arrays contiguous
before viewing bytes; kernel arithmetic is unchanged. The corrected comparison
has completed. [Failed-attempt receipt](tpu-failed-owned-attention-20260919T155459Z.json).

The corrected TPU comparison is healthy and bitwise equal on all 32 chips:

| Selection distribution | Full 2,048 p50 | Bound 512 p50 |
|---|---:|---:|
| Balanced | 1.736–1.753 ms | 0.968–0.974 ms |
| Concentrated on one owner | 1.728–1.739 ms | 1.711–1.722 ms |
| One concentrated row plus an empty row | 1.724–1.731 ms | 1.699–1.712 ms |

Balanced median time falls about 44%; mean falls 1.758–1.762 to 1.084–1.086 ms.
However balanced p99 worsens from 1.885–1.986 to 3.318–3.383 ms in this 30-sample
trial. The conditional executable reserves 87,676,928 temporary bytes versus
84,337,664 for full width: the full fallback is still compiled, so this is no
peak-allocation reduction. Mixed/skewed paths remain near baseline. The option
has not been integrated into a full-model builder or promoted to a default.
[Eight-rank corrected receipt](tpu-microbench-owned-attention-20260919T161535Z.json).

All 14 acquisitions recorded in the cleanup receipt ended with authenticated
idle on all eight hosts, including the failed host-check attempt. No workloads
remain. Final release checks pass (524 passed, 1 skipped; frozen source unchanged),
and the curation ledger is updated with the code and small receipts.

## Bounded buffer prefill integration

The prefill builder now accepts `owned_key_capacity` as an explicit option when
LSE attention is enabled. A private dependency binding supplies that capacity
without changing the frozen gather or module globals. Default behavior is
unchanged. Full CPU32 B114/B128 comparisons use top-K 512 and a 128-key bound:
all returned state/cache/token bit patterns match the full buffer, and finished
states refuse an append without changing committed cache/frontier values.
Six tests passed in 206.24 s, including invalid-option refusal. This integration
has not yet been measured as a complete TPU model. The real-weight DB610 trial
uses full buffers to keep that first comparison localized. The synthetic tool
exposes `--prefill-owned-key-capacity` for a subsequent sole-variant full-prompt
measurement; the primitive's worse p99 remains a reason to measure carefully.


## Pooled routed rows: suffix proof and TPU preparation

The existing from-routes MoE suffix accepts more than 128 rows even though the
complete prefill builder remains limited to canonical B114/B128 windows. The
new CPU32 probe pools 498, 512 and 1,024 rows and compares every output byte
against successive B128 calls (including the B114 tail), with balanced routes
across owners and routes concentrated on one owner. All six cases are healthy,
finite and bitwise equal; the test passed in 15.09 s. BF16 shared projections,
FP8 routed panels, route restoration and both collective axes are included.

`--which prefill_moe_pooling` prepares a real-geometry TPU comparison for a fixed
1,024-row workload split into B128/B256/B512/B1024 calls. This includes grouping,
packing, projections and collectives, with no router or attention. Balanced
B128 has only four live rows per expert in an M32 panel, whereas B1024 has 32;
that suggests less repeated weight decoding, but is not a measured speedup.
The concentrated case tests a distribution with little panel-utilization gain.
The full prefill builder's row limit, dense placement and cache/repair schedule
are unchanged. Full-model integration is justified only if this suffix trial
shows a gain and TPU numerical behavior is acceptable.


The complete TPU suffix comparison finished on all eight hosts (30 samples per
case), followed by authenticated cleanup. For the same 1,024 routed rows:

| Routes | Eight B128 calls | Two B512 calls | One B1024 call |
|---|---:|---:|---:|
| Balanced p50 | 55.690–55.709 ms | 19.711–19.726 ms | 14.371–14.382 ms |
| Concentrated p50 | 55.651–55.658 ms | 52.982–53.004 ms | 53.208–53.227 ms |

Balanced B1024 is about **3.87x faster** for this suffix. Concentrated routing
has little gain and worse B1024 p99 (88.8 ms versus 55.8 ms); B512 p99 is 58.8 ms.
Temporary executable memory rises from 30.3 MB at B128 to 115.3 MB at B512 and
431.0 MB at B1024. All outputs are finite and healthy, but the TPU results are
**not bitwise** despite the CPU proof: maximum absolute difference from B128 is
0.015625–0.03125 across hosts for every larger window. Compiler/collective
rounding is a numerical boundary; the exact source has not yet been isolated.
No full-model builder or serving default changed.

The follow-up `--which prefill_moe_pooling_boundaries` diagnostic compares
B128 with B1024 and returns each owner's routed, shared, shared projection
partial and shared reduced outputs. Only aggregate differences enter receipts.
Returning these values changes compilation, so this acquisition makes no timing
claim. The CPU32 pooling test also verifies these boundaries bitwise across
all 32 owners/features (1 passed, 19.33 s); a TPU result is still required.

Scope correction from source review: the isolated suffix acquisition used the
primitive's default `fp32_route_sum=False` (BF16 route accumulation). Full
prefill explicitly uses FP32 route accumulation. The 3.87x measurement remains
valid for its recorded primitive, but does not measure the complete prefill
suffix's arithmetic configuration. The new full-model pooling candidate keeps
the original FP32 route accumulation.

### P3: prepared wide IndexShare prefixes

`wide_indexshare=True` is a separate opt-in requiring resident BF16 tables,
bounded-owner LSE attention, rolled expert panels, canonical dense placement
and complete cache proposals. Sparse IndexShare windows use one <=128-row
prefix in place of four <=32-row prefixes. Full DSA producers, their M64 repair,
and dense layers retain the existing narrow schedule; embedding/router/MLP
chunking is unchanged. Pooled MoE composes the wider prefix inside its canonical
B128/B114 chunks. Default builders retain the original call graph.

The new layer/cache/row-guard mirrors differ only in their row caps plus an
explicit restriction to sparse IndexShare prefixes; an AST proof pins that
scope. The cache write still validates the complete span and page mapping,
retains per-query causal lengths, ignores padded rows and refuses atomically.
The local attention kernel retains each row's segment order but accepts a
larger row grid only through this private binding. Physical padding to a
multiple of 32 is retained, including the masked 14 rows of a B114 tail. Wider projection/collective
shapes are a TPU numerical boundary; no bitwise TPU or trained-weight claim.
`--prefill-wide-indexshare` compares narrow and wide prefixes with the same
resident weights and initial state. Each variant gets fresh fleet graph consensus,
structural HLO/memory admission, optional trace and a barrier before prompt timing.
After both timed prompts, every addressable shard of the complete output/state
is compared: bitwise differences, finite maximum error and changed nonfinite
values are recorded per leaf. Counts include local replicas; all eight hosts
report independently. Reference state retention is included in live allocator
admission. There is no TPU result for this option yet.


The complete CPU32 proof now passes: a B242 pooled prompt (B128+B114 internal
chunks), top_k 512, owner bound/segment 128 and wide IndexShare prefixes matches
original unbounded B128+B114 execution bitwise in all tokens, caches, selections,
scores and frontiers. Finished-state refusal preserves all committed state
except the failed health latch (1 test, 219.06 s). Cache/option/AST and receipt
checks pass (10 tests, 4.55 s), as do existing LSE and pooling structural tests
(7 tests, 12.98 s). The initial unpadded B114 implementation was rejected:
its first B128 chunk matched, but later cache errors grew to 0.1328125 and DSA
order differed. Preserving the original physical row padding restores the full
CPU bitwise result. A second complete CPU32 case appends the same B242 after
a populated 512-token prefix, exercising sparse selection beyond top-k; every
leaf remains bitwise equal (1 test, 374.18 s). This does not remove the need for
TPU numerical validation.

### P5: divide attention query rows across feature chips

The prefill cache, prepared queries, selected positions and causal bounds are
replicated across feature4. The opt-in `feature_row_attention=True` assigns each
feature chip a contiguous quarter of the query rows for owner-local LSE
attention, then all-gathers the result rows, LSE and per-row health over feature4.
Expert8 head/cache ownership and every per-row arithmetic operation stay the
same. Cache writes, subsequent projections and atomic model commit checks are
outside this wrapper and unchanged. It requires resident LSE rolled windows;
no decode or serving default changes. The replication precondition comes from
the WS32 prefill composition, not an arbitrary-call runtime replication check.

The CPU32 primitive proof passes (1 test, 4.11 s): heterogeneous query rows,
empty selections, balanced and concentrated owners, smaller-buffer/fallback
branches, duplicate selections and selected NaNs all match original output,
LSE and health bitwise. A complete populated-prefix composition proof is running.
An explicit `--which feature_row_attention` probe is prepared to compare full
buffers, bounded buffers and bounded buffers with row splitting at real M32
geometry across balanced, concentrated and mixed rows. No TPU result yet.
